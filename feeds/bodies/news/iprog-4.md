Amazon Aurora DSQL now lets you add foreign key constraints to new and existing tables. Aurora DSQL is a serverless, distributed SQL database with PostgreSQL compatibility and active-active multi-Region availability. Amazon describes Aurora DSQL as offering virtually unlimited scale, high availability, and zero infrastructure management. The original Amazon Aurora began as a MySQL-compatible database engine back in 2014, that was designed to be highly durable and available by automatically replicating data across multiple Availability Zones and continuously backing up data to Amazon Simple Storage Service (Amazon S3). A PostgreSQL version was made available in 2019. Amazon Aurora DSQL is made up of several components including a query processor, adjudicator, journal, and crossbar. Amazon says the components have high cohesion, communicate through well-specified APIs, and scale independently based on your workloads.  The update means developers can express the rules in an application that specify how tables reference each other as Foreign key constraints in the Aurora DSQL cluster. When a rule is defined, such as specifying that a customer's primary address must reference an existing row in the address table, would mean that Aurora DSQL would then refuse any write that would leave that customer pointing at an address that no longer exists. Developers can choose what happens when a referenced row is deleted or updated, with the options including No Action, Restrict, Cascade, Set Null, and Set Default.  The advantage the new feature offers is that it pushes an application's referential integrity logic into the database. Aurora also supports the Match Full and Match Simple match types, and deferrable foreign key constraints. Aurora DSQL maintains referential integrity in two steps: snapshot verification as the transaction runs, and conflict resolution at commit time. Together, these steps guarantee that a committed transaction never violates a foreign key constraint. Snapshot verification means that every transaction in Aurora DSQL runs against a consistent snapshot of the database taken at its start time. When you insert or update a referencing row, Aurora DSQL reads the referenced table at your transaction's start-time snapshot to confirm the referenced key exists. Because the verification reads from the transaction start-time snapshot instead of taking a lock, other transactions can continue to modify the referenced and referencing tables in parallel. Snapshot verification ensures that the constraint held at the transaction's start time, but not between start and commit. A concurrent transaction can delete the referenced row or insert a conflicting referencing row after your transaction started. If such a conflict occurs, Aurora DSQL implicitly applies the Key Share clause to referenced rows to detect whether any concurrent change invalidated your snapshot. If Aurora DSQL detects a conflict, it fails the transaction with a serialization error.  The latest version of Aurora DSQL is available now.
