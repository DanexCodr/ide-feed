While it runs

## Light while it runs.

Ten containers running on one Apple silicon Mac, one runtime at a time: how much CPU and memory each one holds.

- Containers and Compose Every `docker` command you use, Compose projects grouped in the window, and a page for each container with live logs, a shell and its files.
- Images from Docker Hub Search Docker Hub from the window and watch each layer pull. amd64 images run through Rosetta.
- Builds, with a scan `docker build` through BuildKit, a Builds view of every build, and a vulnerability scan of each image on its own page.
- Kubernetes `kiri k8s start` gives you a k3s cluster in about 20 seconds, with Pods and Services in the window. kind runs too.
- Linux machines `kiri machine create dev --distro ubuntu`: your user, sudo, and your Mac folders at the same paths.
- Share A public link for any container on `runkiri.cloud`, from the window or `kiri share web`. [More](https://runkiri.com/share/).
- Names and HTTPS Apps open at `web.kiri.local`, Compose services at `api.myapp.kiri.local`, with HTTPS from Kiri's own narrow certificate authority.
- Light on your Mac Unused memory goes back while it runs, and the VM sleeps after a minute idle. The daemon stays around 15 MB; waking takes 0.15 s.
- Move over in one go Bring your images, volumes and containers from OrbStack or Docker Desktop, then switch `docker` to Kiri from the window.

## The commands you already type.

With Kiri open, the ordinary `docker` command runs on Kiri, and `kiri` adds what Docker doesn't have: a name for every container, Kubernetes, Linux machines and a public link.

- `kiri run`, `kiri ps` work like their docker twins.
- `web.kiri.localhost` reaches a container by name, no port to remember.
- `kiri k8s start` and `kiri machine create` for a cluster or a Linux box.
- `kiri share web` puts it on the internet.

Kiri Share

1. Step 1 Install Open the disk image and drag Kiri to **Applications**. It sets up `docker` for you. [Download for Mac](https://runkiri.com/download/)
2. Step 2 Pull an image Search Docker Hub in **Images** and press Pull, or: `docker pull nginx`
3. Step 3 Run a container Press **Run** and give it a port. It starts in milliseconds. `docker run -p 80:80 nginx`
4. Step 4 Share Press **Share** on the container for a public link, or: `kiri share 80`

Five hops. One shim process stays resident for every running container.

The same five hops, and a shim per running container.

One daemon creates namespaces, cgroups and mounts itself. Nothing per container is left running. Most of this time is the docker CLI starting up. Through the Docker API, a whole container lifecycle takes 3.1 ms.

Medians from one full run on one Apple Silicon Mac, every engine limited to 2 CPUs and 8 GB, all three through the same docker CLI with Docker's default bridge networking. Stops are drawn evenly; only the totals are figures. Windows has [its own race](https://runkiri.com/windows/#numbers).

### Boot once

One VM serves every container. Cold boot to ready takes **112 ms**, down from 810 ms on a stock kernel.

### Talk directly

Requests cross one vsock channel into the VM, not a chain of Unix sockets. A round trip takes **31 µs**.

### Leave nothing behind

No process stays per container. OrbStack keeps a shim for each one: 143 running containers held **1.13 GB** in shims on our test Mac.

Measured on one Apple Silicon Mac. Method and raw numbers are on the [benchmarks page](https://runkiri.com/benchmarks/).

The app

## A native app, not a web wrapper.

AppKit and the system WebKit on the Mac, Win32 and WebView2 on Windows, so no Electron and no bundled browser. Manage containers, images, volumes, networks and Compose projects, with live stats, logs, a terminal and files for each container. Running apps open by name at `myapp.kiri.local`. On the Mac it brings your images and volumes over from OrbStack or Docker Desktop, and lives in the menu bar.
