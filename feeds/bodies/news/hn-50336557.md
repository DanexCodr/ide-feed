Our gate remotes send on 433 MHz, and I wanted to see what those signals looked like. A cheap AliExpress copy remote couldn’t learn them. So I put a CC1101 radio module on a CJMCU-232H, an FT232H board that plugs straight into the laptop. Six jumper wires and a Python script: no microcontroller to flash, nothing to solder.

This setup and test was just to prove that the FTDI board could be connected to the 433 MHz board (bought from AliExpress), and that together they could scan and visualise simple signals from a bootleg remote.

![A drawing of the rig: a terminal window shows green signal bars with one tall spike at 433.92 MHz, a purple FT232H board with a USB plug sends six coloured wires to a small blue CC1101 radio module with a black antenna, and a key fob sends radio waves at the antenna](https://blog.jacq.cc/_astro/cover.V1uv2K4k_Z15X8TA.svg)

*The rig, drawn: the FT232H board, six wires, the CC1101 and its antenna.*

- A CC1101 433 MHz module and its antenna. Mine is an E07-M1101D (Ebyte’s board layout, with an SMA socket), about AU$3.40 on AliExpress.
- A CJMCU-232H: a purple board with an FTDI FT232H chip and a USB-A plug.
- A breadboard, 4 male-female jumper wires and 2 female-female ones.
- Linux with Python 3. The script uses pyftdi.
- Something that sends on 433 MHz to test with. I used the copy remote.

The CC1101 talks SPI. A plain USB-serial stick (CP2102, CH340) only does serial, so it can’t drive it. The FT232H does SPI from USB, so Python on the laptop talks to the radio directly. The usual way is an ESP32 running ESPHome, which means building and flashing firmware every time you change something.

- rf-scan-ft232h.py: the scanner
- keeloq-capture-ft232h.py: sets up the CC1101 and samples its data. The scanner uses it, and on its own it captures KeeLoq remote presses
- keeloq-check.py: the KeeLoq decoder both of them use
- 70-ftdi-ft232h.rules: a udev rule so your user can open the board

All four are [MIT licensed](https://blog.jacq.cc/cc1101-scanner/LICENSE). Keep the three scripts in one folder.

The rule tags the FT232H (USB ID `0403:6014`) with `uaccess`, so the logged-in user can open it: no sudo to run the scanner. Plug the board in after reloading the rules, or unplug it and plug it in again. `--self-test` needs no hardware: it decodes synthetic noisy presses, and a real frame from my copy remote.

The CC1101’s header prints only pins 1, 2, 7 and 8. Pin 1 is the square pad, the odd pins run along the board’s edge, and the even pins sit on the inside.

| 1 | `GND` | `GND` on the 4-pin header |
| 2 | `VCC` | `+3.3V` on the 4-pin header. **Never `+5V`**, and not `VCORE` |
| 4 | `CSN` | `AD3` |
| 5 | `SCK` | `AD0` |
| 6 | `MOSI` | `AD1` |
| 7 | `MISO` / `GDO1` | `AD2` |
| 3, 8 | `GDO0`, `GDO2` | not connected |

Use a terminal window at least 60 × 20. Before the screen starts, the script checks the radio: it reads the chip’s version (mine says `0x14`), writes its settings and reads them back, and checks it’s receiving. If something fails, it names the wires to check. “No CC1101 answers” means power, `SCK`, `MISO` or `CSN`. Settings that read back wrong mean `MOSI`.

It only receives. It never transmits.

The copy remote sends EV1527-style codes: 24 bits, a 20-bit ID (`0x0B80A`) and 4 button bits. Its buttons send `0x0B80A1`, `0x0B80A2`, `0x0B80A4` and `0x0B80A8`. The shortest pulse (TE) is 340 µs. The presses came in at −18 to −20 dBm, against a floor of −88 dBm. A remote repeats its code while the button is down, so each short press gave 3 to 7 frames.

Holding the buttons down fills the list with shorter codes too, 12 to 22 bits long, like `0x80A4` and `0x0B80`. They’re pieces of the real codes that noise cut short. Only the 24-bit rows are real.

*Buttons held down: the four real codes, and pieces of them.*

The script sets the CC1101 up as an OOK receiver on 433.92 MHz, with Flipper Zero’s AM650 settings: a 650 kHz filter and no packet handling. The chip puts the demodulated data on its `GDO1` pin. On this module `GDO1` shares a pin with `MISO`: while `CSN` is high, nobody is talking to the chip and `MISO` carries the data.

The FT232H is already in SPI mode to talk to the radio, and an SPI read clocks bits in at a steady rate. So the script opens a second SPI port on a chip-select pin that isn’t wired, `AD4`. Reading from it leaves `CSN` high and clocks `MISO` in at 50 kHz: a sample every 20 µs, about 17 of them per 340 µs pulse. A thread keeps the USB reads back to back, and the decoder turns runs of ones and zeros into pulse lengths.

When the radio is idle, its output on my rig is mostly high with short dips. That noise often runs straight into the start of a frame and swallows the first bit’s high pulse. Every frame of the copy remote came out 23 bits long instead of 24. The fix: read that bit from its low pulse alone. In EV1527 a 1 is a long high and a short low, and a 0 is a short high and a long low.

For the sweep, the script tunes to each step, waits 1.2 ms for the chip to calibrate and settle, and reads its RSSI register. The filter is set as wide as the step, so a sweep leaves no gaps between steps.

The test was quite successful, and the TUI proved quite handy for learning and seeing what these remotes can output.

The next project builds on this one: scanning the Richmond gate remotes to see what they output and what that looks like. They’re the same remotes that [open our garage through a GE-RCV1](https://blog.jacq.cc/guides/ge-rcv1-garage-gate-remote/). Inside each one is a Microchip HCS300, a KeeLoq rolling-code chip. A rolling-code remote shouldn’t send the same thing twice. Each press is a 66-bit frame: the remote’s serial number and buttons in the clear, and a 32-bit encrypted part that holds a counter, which goes up on every press.

I’ll also try to match the signal with known OEM keys: KeeLoq’s manufacturer keys, which each remote’s own key is made from. If I find a matching key, I won’t publish what the key is, only that I was able to find it, whether from an OEM list or by brute force.

I’m quite excited about this next part of the experiment: it’s becoming quite a little sleuthing puzzle to solve.
