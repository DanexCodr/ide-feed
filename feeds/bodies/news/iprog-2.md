The Keep the Why project is a comprehensive framework and coding agent skill designed to capture, structure and preserve the reasoning behind software development decisions. Created as a deliberate homage to Keep a Changelog, its core philosophy is summed up in its slogan: _"Keep a Changelog records what changed;_  
_Keep the Why preserves why it changed"._ The issue that it addresses is that, when developers and AI coding agents work together, critical decisions happen during the conversation; however, once the chat session ends, that context evaporates:

  * The code shows what was built, but not why. Tests confirm expected behavior, but do not explain why an awkward workaround or defensive loop was necessary.
  * AI Coding Agents suffer from a "goldfish memory" problem; a fresh agent session starts without memory of previous turns, often re-proposing previously rejected implementations or undoing subtle fix workarounds.
  * Missing reasoning leads to repeated mistakes, re-litigating settled architectural decisions, slow developer onboarding and code becoming unmaintainable "legacy" code because nobody remembers why it was written that way.

Keep the Why is built around repo-native project memory. It relies on the principle that your repository is already the single source of truth for your project. All rationale is saved as human and machine readable markdown files in a dedicated context/ folder. Being Git-native, the rationale updates in the same Git commit or Pull Request as the code change itself. It is branched, reviewed, merged and cloned alongside the code. The four main modes of operation are:

  1. Continuous Capture: During normal daily work, the agent proactively notices when rationale surfaces (such as a trade off, a rejected alternative, or a workaround) and records it automatically alongside the code.
  2. Retrospective Recovery: On existing or legacy codebases, the agent scans Git history, issues, PRs and code to reconstruct past reasoning, explicitly marking unverified claims as "unknown" rather than inventing explanations.
  3. Knowledge Transfer Interview: Before a key maintainer leaves or transfers, the agent analyzes the codebase for gaps and conducts an interview (via targeted questions or free narration) to capture tacit knowledge.
  4. Maintenance: Keeps recorded rationale fresh by marking superseded decisions, resolving contradictions and splitting oversized topic files.

From those modes, Continuous Capture is the primary, day to day mode of Keep the Why. It operates on a simple premise; when developers and AI coding agents work together, critical design rationale and trade offs surface naturally in conversation. Rather than making documentation a separate, tedious step after the code is written, continuous capture records that reasoning as a byproduct of normal work before the session ends and the context evaporates. Thus, instead of batching updates into a giant summary at the end of a long session where key details often get forgotten the agent updates the relevant Markdown files in context/ at the exact point the rationale becomes clear (such as right after a workaround is explained or a trade off is settled). If a topic file already exists for that subject, the agent updates it in place. Saying that, there are conversations that are worth capturing and those that are not. As such, Continuous Capture focuses strictly on durable reasoning that code alone cannot explain.  Those worth capturing include:

  * Decisions between real alternatives where the chosen path isn't obvious from the code.
  * Workarounds for external limitations, such as library bugs or API quirks.
  * External constraints (business rules, legal requirements, rate limits).
  * Incidents and bugs, including what changed as a result.
  * Counter intuitive code that looks like it could be simplified or cleaned up, but shouldn't be.
  * Abandoned changes, when starting to modify code and stopping because a hidden constraint surfaced. This "negative space" rationale is especially vital because no Git commit, diff, or PR ever results, making continuous capture the only place this insight survives.

On the other hand, those not worth capturing are:

  * Routine implementation details that the code already explains clearly.
  * Open, undecided choices.
  * Purely speculative ideas ("we might try X later") unless actively shaping current decisions.

The project consists of the required core components, the Agent skill and the repository files, and three optional companion tools:

  1. The Agent skill (SKILL.md) is a lightweight package of instructions, reference docs and examples in the open Agent Skills format. It teaches 70+ supported coding agents (such as Claude Code, Cursor and Codex) how to perform continuous capture, retrospective analysis, knowledge interviews and documentation maintenance.
  2. The project configuration (.keep-the-why) is a committed text file at the project root containing project settings, unique UUID/remote IDs (id), context paths, confirmation rules and schema versioning (context-schema).
  3. The context directory (context/) is a flat folder where rationale lives as plain Markdown versioned by Git.

These optional companion tools are not required to run Keep the Why; instead they extend its capabilities:

  1. keep-the-why-lint: A Python package and GitHub action that validates the mechanical structure of context/ files, index consistency and .keep-the-why formatting locally or in CI pipelines.
  2. The Registry and Globe: A public text registry (registry/projects.txt) and global visualizer that maps cross repository citations, allowing teams to walk through linked "thoughts" across independent repositories.
  3. keep-the-why-dashboard: A read only CLI viewer and static web exporter (for GitHub/GitLab Pages) that renders topic graphs, timelines, Git authorship and decision statuses without modifying repository data. It visualizes a project's recorded rationale, configuration and Git history by transforming Markdown entries and Git metadata into several interactive views.

All fine, but what are some cases of Keep the Why in action, that demonstrate how it captures rationale during a session and prevents repeated mistakes later? As it happens, the most valuable use of Keep the Why is capturing negative space decisions, where an optimization or cleanup was investigated and abandoned. Because no code is modified, there is no Git commit, diff, or pull request to record why the change was stopped.  For instance, trying to simplify "ugly" code, a developer opens a coding session in their project and asks the AI agent: _"This retry_with_jitter wrapper in src/gateway.py looks over engineered. A plain retry loop would do the same thing. Let's simplify it."_ While investigating, the developer or agent realizes that the payment gateway's rate limiter sends a custom Retry-After header. A plain, fixed-delay, retry loop would fire before the rate limit resets, causing repeated HTTP 429 errors under load. They decide to abandon the simplification and keep the existing wrapper. The code remains completely untouched. Because Keep the Why is running in proactive mode, the agent recognizes that a trade-off was evaluated and abandoned. Right in that moment, it writes an entry into context/retries.md.  
Once a decision, or rationale, is recorded in the project's context/ directory, it becomes a plain markdown asset versioned and distributed alongside the codebase by Git. This enables:

  * Stopping AI agents from repeating past mistakes with automatic pre-checks. Future AI coding agent sessions read context/index.md before making non trivial code modifications. If a task touches a specific subject, the agent reads the relevant topic file first.
  * Preventing re-proposals. The recorded entry informs fresh AI sessions about previously attempted and rejected implementations, external constraints and intentional workarounds, preventing agents from re-proposing flawed code.
  * Faster execution. Having rationale stored directly on disk allows AI sessions to start where previous conversations left off, avoiding the need to re-evaluate trade offs from scratch.
  * Enhancing code reviews and pull requests. As it updates context/ files in the exact same Git commit or pull request as the code change itself, reviewers can inspect the code diff alongside the rationale diff to see why an approach was chosen, which alternatives were considered and which constraints applied.
  * Agent-to-Agent communication. A coding agent can record the rationale during development, allowing an AI or human reviewer to review and verify that rationale in the PR.

That last part of Agent-to-Agent communication begs the comparison; is Keep the Why similar in purpose to the tools described in the IProgrammer articles [cq: A Shared Knowledge Commons for AI Agents](<https://www.i-programmer.info/news/105-artificial-intelligence/19009-cq-a-shared-knowledge-commons-for-ai-agents.html>) or [Stack Overflow For Agents](<https://www.i-programmer.info/news/105-artificial-intelligence/19107-stack-overflow-for-agents.html#google_vignette>). While Keep the Why shares a broad underlying goal with cq (A Shared Knowledge Commons for AI Agents) and Stack Overflow for Agents (SOFA), that is, stopping AI agents from repeating costly mistakes and re-discovering solved problems due to "agent amnesia", it differs significantly in purpose, scope, infrastructure and knowledge domain. The cq and SOFA (Global Knowledge Commons) platforms act as a collective "Stack Overflow for AI Agents". They focus on general, cross project technical knowledge such as undocumented API quirks, library version conflicts, configuration bugs and reusable deployment blueprints. The goal is to allow thousands of independent agents working on different systems to share empirical solutions so no agent wastes tokens repeatedly debugging a widespread issue. Keep the Why, on the other hand, is driven by a repo-native rationale; it is deliberately narrow and project-specific and does not attempt to be a general knowledge base or record external library facts. Instead, it records the internal reasoning behind a specific codebase, noting why a function is defensive, why an obvious optimization was tried and rejected, or which internal business constraint shaped the design. cq uses a tiered architecture starting with a local SQLite database, moving to an organizational Postgres vector database for team search and escalating to a hosted public "Global Commons" (cq.exchange). SOFA relies on web API endpoints and public infrastructure for voting and trust scores. Keep the Why uses zero infrastructure there is no central server, no database, no daemon, no cloud account and no vector store. All rationale is saved as plain markdown files in the repository's context/ directory and versioned directly by Git alongside the source code. cq and SOFA are verified through community feedback, trust scores and votes from agents and human operators (e.g., flagging entries or submitting worked_as_written ratings). Under Keep the Why, governance happens directly through Git code reviews. Because rationale lives in context, updates ship in the same pull request as the code change itself. Human maintainers and AI review agents inspect the rationale diff next to the code diff before merging. Another concept that feels close to Keep The Why's rationale is Architecture Decision Records (ADRs). So how do they compare to it? ADRs are the established engineering standard for recording major architectural choices; Keep the Why expands on ADRs rather than replacing them. ADRs are written manually by developers, requiring a separate, deliberate documentation step that often gets skipped under tight deadlines. Keep the Why on the other hand synthesizes them automatically as a natural byproduct of normal conversation while work is happening. You could look at them as dynamic/runtime ADRs. ADRs then, are focused on a few high level, discrete fixed in stone decisions (e.g., "Use PostgreSQL instead of MongoDB"). Keep the Why, on the other hand, covers major choices plus the larger, messier volume of daily, smaller rationale, defensive retry intervals, API rate limit quirks, startup ordering constraints and abandoned refactors. While ADRs rarely capture small investigations or abandoned refactors ("negative space") because no formal decision document is created, Keep the Why specifically captures abandoned attempts where an investigation or simplification was dropped due to a hidden constraint, that way recording why nothing changed, so future sessions don't repeat the mistake. The key takeaway is that while ADRs remain ideal for major, high-level architectural choices, Keep the Why sits directly beneath ADRs, capturing the continuous stream of daily rationale that usually evaporates when sessions end. Enough talking; I'm sold. How do you go about installing it? Just tell your coding agent: _Install the Keep the Why skill pick the best installation method for you from<https://keepthewhy.com/installation/> then set up Keep the Why in this project with default settings, including autostart._ That is the whole setup. Now you are set to go!  And yes it is open source and hosted on Github. Link below. In sum, Keep the Why is essential because it preserves non-obvious code rationale, rejected alternatives and operational constraints as Git-versioned markdown directly in the repository, thus preventing AI agents and human developers from repeating past mistakes or re-investigating already rejected decisions.
