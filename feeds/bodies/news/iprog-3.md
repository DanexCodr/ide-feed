If you want proof that the world of software is insane, you need look no further than the news that Google Chrome now comes with HTML-in-Canvas. How many rendering options does one app need? HTML was a great idea - a simple declarative language for laying out text pages with a bit of graphics. Then things got a bit more interactive with buttons and text boxes, and it was clear that HTML was a language that specified the rendering of a set of graphical objects, including text, onto a web page. From there graphics became ever more important. Various mostly failed attempts at making free graphics easier were introduced but the two that persisted are SVG and Canvas. SVG is interesting because it is a vector drawing language and it can draw directly into the DOM. The DOM or Document Object Model is essentially a representation of all of the graphics objects drawn in the HTML page. This is where HTML elements are rendered and SVG graphics are rendered into the DOM and are treated as equals with other HTML objects - although they are far less often used in practice. In principle SVG can be used to draw anything directly into the HTML page. Canvas is a bitmap graphic object that can be placed in an HTML page and it provides another rendering surface. Again, in principle, Canvas can be used to draw all over the HTML page. What is more, you can use SVG to draw on the canvas as well as on the DOM-controlled HTML page. Confused? Well, it isn't too bad, but yes, there are two distinct rendering surfaces in a web page and at least three languages that can write to them: HTML to the DOM, SVG to the DOM and Canvas and JavaScript to Canvas.  To add to this, we now have HTML-in-Canvas, which allows HTML to render onto the Canvas. Using it is mostly trivial - the HTML that you would have rendered to the DOM you can now simply sandwich between canvas tags:

    <canvas style="width: 400px; height: 200px;"  
                                content="drawable">     

      <form drawable>
        <label for="name">name:</label>
        <input id="name">
      </form>
    </canvas>

and the input box and label now render on the canvas.  The new feature is available in Chrome 157 running on the desktop, Android or on iOS. It isn't a standard as yet, but WHATWG are working on making it a standard. This said, currently Firefox isn't working on it and has reservations, and Safari lists it as unsupported. There is no news on Edge, but given it tends to follow Chromium, it should support HTML-in-Canvas soon. VIDEO So what is the point? Well, with some temporary reservations, you can now use Canvas to render your entire web page. In addition, you can use Canvas graphics commands to draw anything onto the page and make things generally more freeform. Also, given that Canvas supports the use of WebGL, you can now freely mix 3D graphics with your HTML controls.  It has to be admitted that much of this could have been achieved using existing tools. For example, you could place a canvas behind the HTML page and keep the two in sync. The same approach allows the mixing of SVG with HTML. However, it has to be admitted that there are downsides to this approach and HTML-in-Canvas is going to provide a more frictionless ability to mix the two.  So, now with HTML-in-Canvas, we can draw HTML, SVG and canvas graphics directly to a canvas element. The only real question is why we didn't do this in the first place. The browser's rendering surface is just a bitmap and why all of the browsers "languages" haven't just got access to the page is difficult to understand. I suppose we are the prisoners of history. If I wanted to get to this nirvana, I wouldn't have started from the primitive HTML page back at CERN, but with a more ambitious design. It probably is too late to rationalize. Some are suggesting that this new feature will result in more intrusive advertising, but I don't think that is going to be a problem until the standards are ratified and support is more widespread. In the meantime, there are some really nice demos.
