The trouble with testing and developing for rack-scale hardware is that rack-scale is
not all that easy to come by. I mean, nevermind the whole DDR5-as-a-currency thing;
even if all the parts were available in abundance, any completed racks go swiftly
to the front lines (AKA our customers' data centers).

As a member of the Product Assurance Team at Oxide, I find that totally unfair
yet completely reasonable. And so we have to get a bit creative. We have to be
able to:

- Replicate diverse customer networking topologies
- Run our actual control plane
- Test up to date versions of our software
- Represent the hardware components (we make racks, after all) including our switches and microcontrollers

And the cherry on top: we need to do that without cutting special "test version" releases.
Because we want to keep our CI sleek, but also because that wouldn’t be playing fair.

Now, don’t get me wrong — we’re not without our tricks. When I joined Oxide last year,
one of the first things I was introduced to was our *racklettes*; that is, smaller
than average racks of four sleds and two switches each. These racklettes can be
initialized and run just like a real rack, precisely because they *are* a real rack.
Just not in any form factor it would be economical to sell. But for testing they
work like a charm. We have four of them today, soon to be eight, where we can test
any combination of hardware/software requirement.

We also have our various simulated methods of running Omicron. You can read more about
those at [How to Run Simulated](https://github.com/oxidecomputer/omicron/blob/main/docs/how-to-run-simulated.adoc)
and the full(er) [How to Run Guide](https://github.com/oxidecomputer/omicron/blob/main/docs/how-to-run.adoc). I
won’t go into a ton of detail here, but suffice it to say that most parts of our control plane (and more) can be run independently, in tandem, and in various degrees of simulation.

Do you remember the game Q*bert? It was one of the first wildly popular isometric
games, and looked a little like this:

Why am I showing you a ridiculously small game screenshot? Well, each cube in that
image represents a 'voxel,' or a point in 3D space. It’s actually the 3D version of a
pixel. Volume Element + Pixel = Voxel. Neat, right?

Anyway, for Oxide, Virtual OXidE Labs (or Voxel) means an incredible amount of
fidelity packed into a single piece of hardware. It is the spiritual successor to
our prior virtual labs (known as a4x2) which allowed us to hack out decent racks
running in VMs.

Pay attention to that word "fidelity" by the way.
For it is, as Bryan Cantrill puts it, [the Prime Directive](https://oxide-and-friends.transistor.fm/episodes/emulating-oxide-how-faux-can-you-go): labs should use
stock Oxide software without hack or modification.

This is what Voxel gives us. A complete software emulation stack, built on illumos
in Rust, where we can build and test a variety of realistic configurations:

- Sled virtualization provided by [Propolis](https://github.com/oxidecomputer/propolis)
- BGP (numbered and unnumbered) or static networking with Debian and [FRR](https://frrouting.org/)
- P4-powered switches via Oxide’s own [SoftNPU, a software P4 switch](https://netstack.fm/episodes/oxide-networking-with-ryan-goodfellow)
- Microcontroller simulation and emulation for our Service Processor (SP) and Root of Trust (RoT)

And what’s more, it gives us all these features in a fairly small footprint. At home,
I run Voxel labs on a Minisforum MS-A2 mini-PC with a 32-thread AMD Ryzen 9 9955HX and
96GB RAM. On that computer, I can spin up 6 sleds with ease, either in the form of
one rack or in a multirack configuration (two separate racks, one management plane). All
it requires is [Oxide Helios](https://github.com/oxidecomputer/helios) and a decently
fast NVMe drive. Launch, and in about 10 minutes you have a full Oxide rack with each "sled"
in its own Propolis VM — alongside switches (also in Propolis) and other infrastructure.

Remember how I said we have to use stock Oxide software? That actually makes things
easier. The first thing we do (following a common practice in hypervisor tooling) is
to create a reusable snapshot.

Oxide sleds are only ever one of two things: a normal
sled (a "gimlet" for the first generation, "cosmo" for the current) or a "scrimlet,"
which is a sled wired to the sidecar switches that runs a switch zone. It’s all
amazingly elegant in its complexity, you should read more about it in
[our networking docs](https://docs.oxide.computer/guides/architecture/networking).

To create a snapshot for Voxel, all we must do is create a "sled" (virtual machine),
install our control plane (Omicron) on it, snapshot it before the point of configuration,
et voilà: a ready-to-launch sled. The control plane can be installed one of two ways:

Voxel clones the [Omicron repo](https://github.com/oxidecomputer/omicron/) on GitHub (or uses a locally defined source for rapid development) and uses `cargo` to compile

We use [Tufaceous](https://github.com/oxidecomputer/tufaceous) to package Omicron releases using The Update Framework (TUF) and our CI tool [Buildomat](https://github.com/oxidecomputer/buildomat/)

Like I said, a lot of steps. Here’s what happened:

1. Trust material is generated in the form of [sprockets PKI](https://rfd.shared.oxide.computer/rfd/0238)
2. Emulated STM32H753 and LPC55 microcontrollers are flashed with [Hubris firmware](https://github.com/oxidecomputer/hubris)
3. Our [automated network topology suite](https://github.com/oxidecomputer/falcon) (known as falcon) wires the topology with simnet and VNIC pairs for every link, and stages the sleds (g0, g1, and g2 in this case)
4. Propolis VMs launch; 6 total in this example, with 3 driving the network and 3 as Oxide sleds
5. `voxel-init` runs: a lightweight Rust agent on each node thatSets up NAT and uplink addressingConfigures underlay setup on each sledWrites the M.2 partition layout on emulated boot disks and labels five U.2 data disksSeeds the host phase 2 image and install dataset to the M.2sAssigns the scrimlets and runs a switch enforcer so they "remember" their identity across restartsActivates `sled-agent`, the per-sled configuration layer for the control plane
6. Connects to the commission API for `wicketd`, which brings the rack through its initialization phases

It’s a complex dance of steps, and I really buried the lede on the whole "emulated
microcontrollers" front. But suffice it to say these are the complete and right steps for
any Oxide rack, except the hardware is represented as distinct pieces of code. For example,
need a new interconnect between two virtual racks? Add a couple lines of code in `rack.rs`.

There are a *few* things that don’t follow the Prime Directive (yet!). For example, those certs
that make up the sprockets PKI up top aren’t set at manufacturing and coming from the RoT
like our production racks. But that’s one of those things that we can live with for now, as
it doesn’t affect actual rack runtime.

This is the bit I mentioned a moment ago. A big part of what makes our racks unique is
the embedded [RoT and SP](https://docs.oxide.computer/guides/architecture/rack-components#_service_processors)
in every sled. We’ve long had an `SpSim` construct that served as a stub for the service
processor and would return the right info at the right times. But that’s simulation, not
emulation. It’s always going to be happy path, and that’s just not enough fidelity for
real testing cases.

As such, we built actual emulated Cortex-M7 and Cortex-M33 devices for illumos and Linux
(x86 and ARM). The [repo for this tool (sp-emu)](https://github.com/oxidecomputer/sp-emu)
is open source. Each of the two devices runs in a single thread, and (mostly)
faithfully emulates the three main requirements: instructions, time, and interrupts.

From there, you can flash our Hubris firmware directly to these emulated devices, and then
communicate by way of an ordinary socket. The Voxel lab can speak with these virtual devices via the
Management Gateway Service (MGS) and Inter-Processor Communication Channel (IPCC). You can learn
everything you want and more about these concepts in the [Management Gateway Service repo](https://github.com/oxidecomputer/management-gateway-service/) and [Hubris docs](https://hubris.oxide.computer/reference/).

There really is no "run real microcontrollers as virtual devices with this one neat trick!"
I can think of. But the real challenge of sp-emu’s job is time. Remember all of the code
we’re running there is meant for silicon. Hubris schedules off a 1ms SysTick and the emulator doesn’t
use wall time; as such, we had to invent a clock. That said, emulated hardware is also
*slower* than the real thing. So there’s…​ well, less time per time. So instead of trying
to get all temporal about it, time became instructions. For example, I give you `maybe_tick`:

```rust
if self.systick == 0 {    self.systick = self.syst_rvr;}self.systick -= 1;if self.systick == 0 {    self.systick = self.syst_rvr;    self.tick_events = self.tick_events.wrapping_add(1);    if self.syst_csr & 2 != 0        && self.mode == Mode::Thread        && !self.primask    {        self.exception_entry(15, bus); // SysTick exception    }}
```

In this case, we count instructions against the kernel’s own reload value and fire exceptions
anywhere the single-priority design makes it safe to take it — in thread mode, interrupts
unmasked. By the same token, peripheral access costs one tick of our clock (an instruction),
whereas on silicon it might stall for dozens of cycles on the bus.

You may have noticed `self.exception_entry` which is defined
elsewhere in the code:

`fn exception_entry(&mut self, vecnum: u32, bus: &mut Bus)`

In short, this function models everything the hardware does on a Cortex-M core taking
an exception, all the way between "exception becomes active" to the first handler
instruction. `vecnum` here is an ARMv7-M exception number (also the vector table index
for that exception’s handler). `bus` is the memory system which is used to actually
push the frame and read the table.

Hubris has a non-preemptible kernel, though it schedules tasks preemptively. SVCall,
PendSV, SysTick and all IRQs run at the same
priority level, while faults keep a higher priority. As such, the emulator doesn’t have
to nest handlers. It processes pending IRQs based on the PRIMASK, FAULTMASK, and BASEPRI
settings. If one of them pended PendSV, that will perform the deferred context
switch for the kernel. For more details on how it works internally, you can check
[this lovely bit of documentation](https://github.com/oxidecomputer/hubris/blob/master/sys/kern/src/arch/arm_m.rs#L5-L71).

```rust
if let Some(irq) = bus.next_irq() {    if self.basepri == 0 || (bus.irq_prio(irq) as u32) < self.basepri {        bus.clear_pending(irq);        self.exception_entry(16 + irq as u32, bus);        return;    }}if bus.take_pendsv() {    self.exception_entry(14, bus);}
```

There’s a lot more we can talk about here, but to sum it all up you can look at this
pseudo-ish loop:

```rust
loop {    cpu.step(&mut bus, host.as_mut())?;   // one Thumb-2 instruction    cpu.maybe_tick(&mut bus);             // SysTick: time is instructions    cpu.maybe_interrupt(&mut bus);        // NVIC and PendSV delivery    if cpu.cycles % 4096 == 0 {        bus.pump_eth(host.as_mut());      // MGS packets in and out        bus.pump_uart(host.as_mut());    }}
```

Note: yes I’m aware I said there’s no cycles then have a field named cycles. That’s the
"fake it till you make it" part of emulation.

That’s the overall heartbeat of sp-emu, and it runs ad infinitum. Everything else exists
to make those calls seem real.
