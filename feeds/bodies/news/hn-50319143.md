Linux's stable kernels shipped a fix on October 11 and 15, 2026 for [CVE-2026-98432](https://www.cve.org/CVERecord?id=CVE-2026-98432), a use-after-free in the IPv4 TCP handshake that a remote, unauthenticated peer can reach. The kernel's own CVE Numbering Authority (CNA) scores it CVSS 3.1 **9.8, Critical**. The fixed releases are **5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10**, and **7.3**, and the bug goes back to Linux 4.4. The upstream fix is a four-line change, but most servers run a distribution's kernel, and as of 8:00 PM CDT, October 29, Ubuntu's tracker still reads "Vulnerable" for its kernel on every release, and Red Hat lists RHEL 8, 9, and 10 as affected with no fix.

Linux from **4.4** on, below **5.10.272 / 5.15.223 / 6.1.190 / 6.6.159 / 6.12.113 / 6.18.56 / 7.2.10**. Distribution kernels follow their own versions: check the tracker.

**Why it's urgent:** the bug sits in code every Linux server runs when it accepts an IPv4 TCP connection, before any application sees the connection. Anthropic, whose researcher reported it, says its Claude model wrote a working proof-of-concept exploit that runs commands as root on "Linux servers with a multipath TCP listener," with no credentials. See the [timeline](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#timeline-and-exploitation-status).

## [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#how-the-vulnerability-works)How the vulnerability works

When a Linux server accepts a TCP connection, the kernel tracks the half-open handshake in a lightweight "request socket," then creates a full socket once the handshake completes. If the connecting peer's IPv4 header carried options, the kernel keeps them to echo in its replies. The bug: the kernel handed those saved options from the request socket to the new connection without copying them, then freed them immediately when the connection went away, while another CPU could still be reading them to build a handshake reply. Reading freed kernel memory is a use-after-free.

The peer needs no login, and it all happens inside the kernel's handshake handling, before any application code runs. The CNA's scoring notes say the stale data can leak kernel heap memory back to the peer, steer kernel writes out of bounds, or crash the machine. Anthropic says a lost race "only fails the handshake without crashing the whole system, so a determined attacker can retry indefinitely until they succeed."

### [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#the-fix)The fix

Eric Dumazet's commit, "ipv4: free inet_opt and ireq_opt after an RCU grace period," changes two plain `kfree()` calls to `kfree_rcu()`, which waits until every reader has finished with the memory before freeing it. Other code paths that replace these options already did that. The commit also fixes the same problem in request-socket migration (`net.ipv4.tcp_migrate_req=1`, or a `BPF_SK_REUSEPORT_SELECT_OR_MIGRATE` program), and says a related IPv6 case "will be addressed in a separate patch."

## [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#which-servers-are-exposed)Which servers are exposed

- Every Linux host that accepts IPv4 TCP connections on an affected kernel: web servers, SSH, databases, load balancers, and Kubernetes nodes. The CNA's notes say the vulnerable path runs "during the TCP handshake, before application authentication."
- Hosts with a multipath TCP (MPTCP) listener first. That's the setup Anthropic's working exploit needs: "Linux servers with a multipath TCP listener." Anthropic hasn't said why that listener matters, and the CVE record doesn't mention MPTCP. A server has one only if an application opens an MPTCP socket; the check is below.

**Red Hat rates the bug lower than the CNA.** It scores the attack complexity as High (CVSS 8.1) and describes the result as mainly a crash "or potential memory corruption." Anthropic's lab exploit shows a remote root shell on at least one configuration, so a lower rating isn't a reason to wait.

## [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#how-to-check-your-systems)How to check your systems

### [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#check-the-kernel)Check the kernel

Compare the result with your distribution's status [above](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#distribution-status), not with the upstream version. If the installed kernel is newer than the running one, the fix isn't active until you reboot. Run these on container hosts and Kubernetes nodes, not inside containers: a container reports the host's kernel. We ran them on a Debian 12 host and in a Rocky Linux 9 container.

### [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#check-for-multipath-tcp-listeners)Check for multipath TCP listeners

`ss -M` lists only MPTCP sockets, so an empty result means no MPTCP listener. `net.mptcp.enabled = 1` alone doesn't create one: an application has to open an MPTCP socket. We tested both with iproute2 6.1 in a Debian 12 container, where `ss -Mlnp` listed a test MPTCP listener and skipped a plain TCP one beside it.

## [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#how-to-fix)How to fix

### [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#update-the-kernel-and-reboot)Update the kernel and reboot

Install your distribution's fixed kernel as soon as it ships, then reboot: a kernel update doesn't take effect until the machine boots into it. Reboot container hosts and Kubernetes nodes too. Appliances and cloud images that bundle a kernel need their vendor's update.

On Debian, SUSE Linux Enterprise Server 16.0 and the 15 LTSS releases, Oracle Linux's UEK kernels, and Amazon Linux 2023's `kernel6.12` and `kernel6.18`, the fix is out. On Ubuntu, RHEL, Amazon Linux 2, and Amazon Linux 2023's default kernel, it isn't yet, as of 8:00 PM CDT, October 29. Watch the trackers linked [above](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#distribution-status). Running a self-built kernel? Move to the fixed stable release for its line.

### [#](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf#if-you-can-t-patch-yet)If you can't patch yet

Red Hat publishes no mitigation. The following is Atlas's interim recommendation, based on the CNA's scoring notes, which say the attacking peer supplies IPv4 Record Route or Timestamp options in its SYN. TCP traffic almost never carries IPv4 options legitimately, so dropping TCP packets that have them should cost nothing:

`ip hdrlength gt 5` matches any IPv4 header longer than the 20-byte minimum, which only options produce. The rule runs before connection tracking and doesn't touch IPv6 or non-TCP traffic. We tested it in a Debian 12 container: it dropped a SYN carrying a Record Route option, and ordinary TCP connections still worked. We haven't tested it against an exploit, and it doesn't fix the kernel. It lasts until reboot, which is fine if the reboot is into a fixed kernel; remove it with `nft delete table ip cve_2026_98432`. If your edge firewall can drop IPv4 packets with options, doing it there protects every host behind it.

Until then, keep MPTCP listeners off the internet, and put the hosts that have one at the top of the patch list.
