We provide an overview of PostgreSQL 19, highlighting its major performance enhancements, administrative controls and developer features introduced in the November 2026 release. PostgreSQL 19 was delayed from its usual September to mid October release window until November 19, primarily because rapid advancements in large language models (LLMs) led to a massive surge in newly discovered bugs and security vulnerabilities. Several new frontier AI models were released after April's feature freeze of PostgreSQL. These models proved far more capable at analyzing PostgreSQL's complex C codebase and uncovered a large number of deep-seated logic bugs in both newly committed patches and decades old code. As a result, commits to the release branch jumped by more than 60% compared to the previous year and back patched fixes to prior stable branches rose by over 74%. Even when AI tools drafted fixes, human committers still had to review, verify and commit every change, creating a major bottleneck because the number of maintainers did not grow to match the doubled volume of submissions per committer. Nevertheless, the eagerly-awaited release is finally here, and is a practical release focused on operational control, maintenance efficiency, replication and developer ergonomics. Here are its key features: **1\. Workload management and maintenance** REPACK and REPACK (CONCURRENTLY): PostgreSQL 19 introduces the REPACK command to reclaim disk space and optionally reorder table data using an index, unifying and replacing VACUUM FULL and CLUSTER (which remain available for compatibility). With the CONCURRENTLY option, PostgreSQL rebuilds the table while normal reads and writes continue, taking only a brief exclusive lock at the end to swap the files. Smarter autovacuum: Autovacuum can now vacuum table indexes in parallel, controlled by the autovacuum_max_parallel_workers setting. It also adds a configurable scoring system to prioritize which tables need vacuuming or analyzing most urgently, which can be inspected via the pg_stat_autovacuum_scores view. **2\. Query Planning and Performance** Query plan stability: Two new contrib modules, pg_plan_advice and pg_stash_advice, let administrators stabilize or adjust query plans (such as join order, join method and scan method) without modifying application SQL. pg_plan_advice generates and applies plan advice, while pg_stash_advice stores it by query ID and applies it automatically when matching queries are planned. Compression defaults: On builds with LZ4 support, lz4 replaces pglz as the default TOAST compression method. Setting wal_compression to on also now selects the best available compression algorithm instead of defaulting to pglz. **3\. Replication and high availability** WAIT FOR LSN: The new WAIT FOR LSN command lets a session on a read replica pause until the standby has replayed the write ahead log (WAL) up to a specific log sequence number (LSN). This prevents stale reads immediately after a write on the primary without requiring synchronous replication or application side polling Simpler logical replication: When wal_level is set to replica, creating the first logical replication slot automatically raises effective_wal_level to logical, eliminating the need for a server restart **4\. Developer experience and SQL** INSERT ... ON CONFLICT DO SELECT: This addition provides a clean get or create pattern that returns conflicting existing rows via RETURNING without performing a dummy update or requiring a second query. IGNORE NULLS in Window functions: The lead(), lag(), first_value(), last_value() and nth_value() window functions now accept IGNORE NULLS and RESPECT NULLS. COPY enhancements: COPY TO can now export data directly in JSON format (including as a single JSON array with FORCE_ARRAY) and supports partitioned tables. COPY FROM adds ON_ERROR SET_NULL to convert invalid input values to NULL, supports skipping multiple header lines and uses SIMD CPU instructions to accelerate text and CSV imports. Additional functions and types: SQL/JSON path expressions gain string methods such as btrim(), lower(), upper(), replace() and split_part(). The random(min, max) function now supports date, timestamp and timestamptz ranges and a new 64-bit unsigned oid8 data type is included. Finally, **new monitoring views and EXPLAIN options:** PostgreSQL 19 adds pg_stat_lock, pg_stat_recovery, pg_stat_autovacuum_scores and pg_stat_progress_repack. EXPLAIN (ANALYZE, IO) and auto_explain.log_io report asynchronous I/O activity and full page image WAL bytes are now reported in pg_stat_wal, EXPLAIN (ANALYZE, WAL) and vacuum/analyze log. The next version, Postgres 20, as already highlighted sits on top of the core bottleneck during the PostgreSQL 19 cycle with patch submissions per committer more than doubling while the number of committers barely growing and at the same time frontier AI models uncovering waves of security vulnerabilities. Thus the community has made plans to adjust for it that include shifting to a more frequent minor release schedule, every 1.5 to 2 months, so fixes for AI discovered issues reach users faster and that developer workload is more evenly paced , and expanding the committer pool. Will those made any difference? Only time can tell. Till next time...
