- New [REPACK](https://www.postgresql.org/docs/release/19.0/sql-repack.html) command that reclaims disk space and reorganizes table contents, which can improve query performance. `REPACK (CONCURRENTLY)` allows repacking without blocking reads and writes to the table.
- [pg_plan_advice](https://www.postgresql.org/docs/release/19.0/pgplanadvice.html) extension for controlling query planner decisions and [pg_stash_advice](https://www.postgresql.org/docs/release/19.0/pgstashadvice.html) extension that applies plan advice automatically based on the query.
- Better performance in many areas, including automatic scaling of the number of I/O worker processes, quicker foreign-key checks, and further planning and execution optimizations.
- Logical replication can now be enabled without a server restart when [wal_level](https://www.postgresql.org/docs/release/19.0/runtime-config-wal.html#GUC-WAL-LEVEL) is set to `replica`.
- Logical replication of [sequence values](https://www.postgresql.org/docs/release/19.0/logical-replication-sequences.html).
- Support for “read-your-writes” consistency on standbys via the new [WAIT](https://www.postgresql.org/docs/release/19.0/sql-wait.html) command.
- [Parallel autovacuum of table indexes](https://www.postgresql.org/docs/release/19.0/runtime-config-vacuum.html#GUC-AUTOVACUUM-MAX-PARALLEL-WORKERS) and [autovacuum prioritization](https://www.postgresql.org/docs/release/19.0/routine-vacuuming.html#AUTOVACUUM-PRIORITY) through a new scoring system.

The above items and other new features of PostgreSQL 19 are explained in more detail in the sections below.

A dump/restore using [pg_dumpall](https://www.postgresql.org/docs/release/19.0/app-pg-dumpall.html) or use of [pg_upgrade](https://www.postgresql.org/docs/release/19.0/pgupgrade.html) or logical replication is required for those wishing to migrate data from any previous release. See [Section 18.6](https://www.postgresql.org/docs/release/19.0/upgrading.html) for general information on migrating to new major releases.

Version 19 contains a number of changes that may affect compatibility with previous releases. Observe the following incompatibilities:

- Add server variable [`password_expiration_warning_threshold`](https://www.postgresql.org/docs/release/19.0/runtime-config-connection.html#GUC-PASSWORD-EXPIRATION-WARNING-THRESHOLD) to warn about password expiration (Gilles Darold, Nathan Bossart) [§](https://postgr.es/c/1d92e0c2c) The default warning period is seven days.
- Issue a warning after successful MD5 password authentication (Nathan Bossart) [§](https://postgr.es/c/bc60ee860) The warning can be disabled via server variable [`md5_password_warnings`](https://www.postgresql.org/docs/release/19.0/runtime-config-connection.html#GUC-MD5-PASSWORD-WARNINGS). MD5 passwords were marked as deprecated in PostgreSQL 18.
- Remove RADIUS support (Thomas Munro) [§](https://postgr.es/c/a1643d40b) PostgreSQL only supported RADIUS over UDP, which is unfixably insecure.
- Force [`standard_conforming_strings`](https://www.postgresql.org/docs/release/19.0/runtime-config-compatible.html#GUC-STANDARD-CONFORMING-STRINGS) to always be `on` in the database server (Tom Lane) [§](https://postgr.es/c/457620845) Dumps created using pre-PostgreSQL 19 versions of [pg_dump](https://www.postgresql.org/docs/release/19.0/app-pgdump.html) or [pg_dumpall](https://www.postgresql.org/docs/release/19.0/app-pg-dumpall.html), and using `standard_conforming_strings = off`, will not properly load into PostgreSQL 19 and later servers. Users should create dumps using PostgreSQL 19 or later versions of these applications, or use `standard_conforming_strings = on`. Client applications still support operations with servers having `standard_conforming_strings = off`, for compatibility with old servers. The server variable `escape_string_warning` has been removed as unnecessary.
- Disallow carriage returns and line feeds in database, role, and tablespace names (Mahendra Singh Thalor) [§](https://postgr.es/c/b380a56a3) [pg_upgrade](https://www.postgresql.org/docs/release/19.0/pgupgrade.html) will also disallow upgrading of clusters that use such names. This was changed to avoid security problems.
- Change the default index opclasses for [`inet`](https://www.postgresql.org/docs/release/19.0/datatype-net-types.html) and [`cidr`](https://www.postgresql.org/docs/release/19.0/datatype-net-types.html) data types from [btree_gist](https://www.postgresql.org/docs/release/19.0/btree-gist.html) to [GiST](https://www.postgresql.org/docs/release/19.0/gist.html) (Tom Lane) [§](https://postgr.es/c/b3b0b4571) [§](https://postgr.es/c/b352d3d80) The [btree_gist](https://www.postgresql.org/docs/release/19.0/btree-gist.html) `inet`/`cidr` opclasses are broken because they can exclude rows that should be returned. [pg_upgrade](https://www.postgresql.org/docs/release/19.0/pgupgrade.html) will disallow upgrading of clusters with [btree_gist](https://www.postgresql.org/docs/release/19.0/btree-gist.html) `inet`/`cidr` indexes.
- Disallow system columns from being used in [`COPY FROM ... WHERE`](https://www.postgresql.org/docs/release/19.0/sql-copy.html) (Tom Lane) [§](https://postgr.es/c/21c69dc73) The values of such columns were not well-defined.
- Change a [`json_array()`](https://www.postgresql.org/docs/release/19.0/functions-json.html) call which returns no rows to return an empty JSON array (Richard Guo) [§](https://postgr.es/c/8d829f5a0) This previously returned `NULL`.
- Cause transactions to pass their `READ ONLY` and `DEFERRABLE` status to [postgres_fdw](https://www.postgresql.org/docs/release/19.0/postgres-fdw.html) sessions (Etsuro Fujita) [§](https://postgr.es/c/de28140de) This means `READ ONLY` transactions can no longer modify rows processed by [postgres_fdw](https://www.postgresql.org/docs/release/19.0/postgres-fdw.html) sessions.
- Change default of [`max_locks_per_transaction`](https://www.postgresql.org/docs/release/19.0/runtime-config-locks.html#GUC-MAX-LOCKS-PER-TRANSACTION) from 64 to 128 (Heikki Linnakangas) [§](https://postgr.es/c/79534f906) Lock size allocation has changed, so effectively settings must now be doubled to match their capacity in previous releases.
- Remove server variable `io_workers` (Thomas Munro) [§](https://postgr.es/c/d1c01b79d) This has been replaced by four new variables; see [Section E.1.3.1.2](https://www.postgresql.org/docs/release/19.0/release-19.html#RELEASE-19-PERFORMANCE).
- Change [JIT](https://www.postgresql.org/docs/release/19.0/jit.html) to be disabled by default (Jelte Fennema-Nio) [§](https://postgr.es/c/7f8c88c2b) Previously JIT was enabled by default, and activated based on optimizer costs, but this costing has been determined to be unreliable. This change requires sites that are doing many large analytical queries to manually enable JIT.
- Change [parallel vacuum](https://www.postgresql.org/docs/release/19.0/routine-vacuuming.html#PARALLEL-VACUUM) leaders and workers to share the cost-based vacuum delay limit (Bharath Rupireddy) [§](https://postgr.es/c/8628df889) Previously each worker process slept based only on the cost it incurred itself, so a parallel vacuum could consume several times the budget set by [`vacuum_cost_limit`](https://www.postgresql.org/docs/release/19.0/runtime-config-vacuum.html#GUC-VACUUM-COST-LIMIT). With this change, [`VACUUM`](https://www.postgresql.org/docs/release/19.0/sql-vacuum.html) with parallel workers and cost-based delay enabled might run slower than in previous releases.
- Rename column `sync_error_count` to `sync_table_error_count` in system view [`pg_stat_subscription_stats`](https://www.postgresql.org/docs/release/19.0/monitoring-stats.html#PG-STAT-SUBSCRIPTION-STATS) (Vignesh C) [§](https://postgr.es/c/3edaf29fa) This is necessary since sequence errors are now tracked separately.
- Rename wait event *type* `BUFFERPIN` to `BUFFER` and rename wait event `BufferPin` to `BufferCleanup` (Andres Freund) [§](https://postgr.es/c/6c5c393b7)
- Remove wait event `BufferContent` and add more precise wait events `BufferShared`, `BufferShareExclusive`, and `BufferExclusive` (Andres Freund) [§](https://postgr.es/c/fcb9c977a)
- Change index access method handlers to use a static [`IndexAmRoutines`](https://www.postgresql.org/docs/release/19.0/indexam.html) structure, rather than dynamically allocated ones (Matthias van de Meent) [§](https://postgr.es/c/bc6374cd7)
- Remove optimizer hook get_relation_info_hook and add better-placed hook build_simple_rel_hook (Robert Haas) [§](https://postgr.es/c/91f33a2ae)
- Change [psql](https://www.postgresql.org/docs/release/19.0/app-psql.html)'s `\crosstabview` command to honor the `\pset null` setting (Chao Li) [§](https://postgr.es/c/4df5fe383)
- Change [full text search](https://www.postgresql.org/docs/release/19.0/textsearch.html) and [pg_trgm](https://www.postgresql.org/docs/release/19.0/pgtrgm.html) to use the database's locale provider for character classification when parsing text (Jeff Davis) [§](https://postgr.es/c/e113f9c102b) Previously, characters were classified using libc, regardless of the locale provider. In databases with a locale provider other than libc (e.g., `ICU`, `builtin`) and where the locale configured through that locale provider behaves differently from the `LC_CTYPE` setting configured for the database, particularly a LC_CTYPE of `C`, the output of some full text search and pg_trgm functions could change. When upgrading such databases using [pg_upgrade](https://www.postgresql.org/docs/release/19.0/pgupgrade.html), it is recommended to reindex all indexes which use full text search and pg_trgm after the upgrade, and to recompute any stored `tsvector` values.
- Change how [fuzzystrmatch](https://www.postgresql.org/docs/release/19.0/fuzzystrmatch.html) functions handle non-ASCII characters (Peter Eisentraut, Jeff Davis) [§](https://postgr.es/c/e39ece034) [§](https://postgr.es/c/b96a9fd76f3) `dmetaphone()` and `dmetaphone_alt()` now upper-case their input using the database's default collation rather than always using libc, and `soundex()`, `metaphone()`, and `difference()` now treat only ASCII letters as letters. When upgrading with [pg_upgrade](https://www.postgresql.org/docs/release/19.0/pgupgrade.html), it is recommended to reindex any indexes that use these functions after the upgrade.
- Remove `MULE_INTERNAL` encoding (Thomas Munro) [§](https://postgr.es/c/77645d44e) This encoding was complex and rarely used. Databases using it will need to be dumped and restored with a different encoding.
