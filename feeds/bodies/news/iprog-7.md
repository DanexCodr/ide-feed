The experimental just-in-time compiler is being removed from CPython. The Python steering committee paused the development of the JIT back in June, and now Savannah Ostrowski, Steering Council Member, has said that after further discussion, the developers working on the proposal for the compiler have decided to withdraw it.  Back in June, the Steering Council told the Python discussion group that when the JIT, Just In Time compiler, was originally merged into main, it entered as an experiment, and the only enhancement proposal written about it, PEP 744, is Informational. PEPs are Python Enhancement Proposals. The statement said that the Steering Council was _"formally requesting a Standards Track PEP be authored that the community can discuss and the Steering Council can formally accept (or reject), making the case for the JIT as a supported, non-experimental part of CPython: its guarantees, its maintenance commitments, and its impact on redistributors."_ _"Until such a PEP is accepted, we ask that no new development on the JIT land on main, including new features, optimizations, and performance work. Bugfixes and security fixes may of course continue as normal; the request is specifically that no further new JIT functionality be added until a PEP has been accepted."_ Council member Pablo Galindo Salgado said that the existing proposal: _"did valuable work in explaining the initial design and even sketched the criteria under which the JIT might become a permanent feature, including questions it explicitly left open: committed long-term maintainers, a security review, debugging and out-of-process tooling support, the guarantees the runtime would make, and the obligations the JIT would place on redistributors and downstream packagers."_ He continued: _We want to be clear that we are not implying that the authors have intentionally bypassed the formal process. The responsibility is a shared one, ourselves included: collectively we (the Steering Council) have not been as strict about following the process as a change of this complexity and reach deserves."_ The alternative route proposed by the Steering Council suggested that for example, rather than proposing one single concrete JIT implementation, it might make more sense for the PEP to describe a JIT infrastructure that can support multiple implementation strategies.  _"We would like the PEP to address at least the following points:"_ _"Maintenance is a real concern for a subsystem of this size and complexity, and the PEP should set out a clear plan for how the JIT will be sustained and maintained over the long term and how it will impact maintainers and contributors that don't directly contribute to the JIT."_ _"How it will keep compatibility with existing CPython features and tooling. How the JIT interacts with, and what it guarantees for, the capabilities CPython already supports. This includes things such as free-threading, profilers, and debuggers, but the PEP should treat this broadly and with nuance rather than as a fixed checklist."_ _"Clear, measurable success metrics and timelines. What the project is aiming for and by when, for example performance targets, platform coverage, and memory overhead."_ _"Relationship to other JIT compilers. Whether the design is intended to provide general infrastructure that other efforts could build on, and whether it is expected to be compatible or incompatible with third-party JIT implementations such as CinderX, Numba, and PyTorch or any other 3rd party JIT."_ _"Whether the current JIT architecture is considered stable, or likely to change further."_ The compiler was added to CPython in 2024 in the 3.13 release by Brand Bucher as an experimental feature, with the encouragement of Steering Council member Thomas Wouters, who was the release manager for Python 3.13.  The council set a window in June of six months for a PEP to be submitted and resolved. If no such PEP is accepted within that window, the JIT code must be removed from the main branch and development must be continued outside the main Python repository. Bucher, Ostrowski, and Ken Jin drafted a PEP 836 to answer the points raised in June, and published it on July 3. The Council said that although this did answer all of the original questions, they still had concerns, wanting more information about support plans and performance criteria, and set out another ten-point list of things that should either be spelled out in the PEP, or at least discussed and rejected. The six months would be up in December. Now Ostrowski has said: _"The Steering Council rightly sets a high bar for a proposal of this scope, and we don't feel we have the personal bandwidth to carry the current version forward."_ Given the withdrawal of the PEP, and the approaching deadline, the JIT will almost certainly be removed from CPython main son enough to be able to sort out any problems caused by removing it before the release of Python 3.16 next year. No-one has commented in public so far whether work will continue on JIT by the original team.  So where does this leave those of us who rely on CPython? The mistake was the inclusion of a feature that wasn't fully decided in the first place. The whole point of having a steering council is to keep Python a trustworthy version of the language that we can all rely on. It's a shame that such a useful feature is removed, but better now than a couple of years down the line when the situation would be a lot messier. If the JIT compiler is good enough, it will make it in eventually - and hopefully this time after full agreement by the steering council. It does raise the question of whether a JIT is worth having? Personally I've always thought that the approach was mostly more trouble than it was worth but I have only slight anecdotal evidence for this view. Clearly JIT compilation only really helps for long running programs with lots of iteration but it slows things down for other programs as they have to wait for the compilation to complete. Making CPython faster is a good objective but a full compiler is an even better option and much more decoupled from the main project.
