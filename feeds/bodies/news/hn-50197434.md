Given that I still have your attention before things get technical again, let's start this post with a hilarious discovery:

### Point items with negative values?

I only discovered this quirk by accident, as another result of [📝 my 2024 code cleanup](https://rec98.nmlgc.net/blog/2024-10-22#cleanup-2024-10-22). Back then, pbg's original formatting code for these point item popups contained one of the numerous code analysis warnings I chose to address rather than ignore:

`e->point` is unsigned, which *surely* means that you can never collect point items with negative values, right? Well, I was just testing a newly changed part of the architecture when this happened:

Surprise, the game does in fact *not* clamp point item values to 0! Looking at [the collection value formula](https://github.com/nmlgc/ssg/blob/dc63b340a7c184b456850972b89324d9a8f13c4f/ssg/internal/Item.cpp#L55) immediately tells us what happens there:

This works fine for regular gameplay where VIVIT's Y position is clamped to exactly 469. It also explains the 0 points you get for collecting point items while bottom-hugging with an empty Evade chain.  

	But once VIVIT collides with anything and loses a life, her Y position is immediately set to 659, before she moves up at a speed of 1.5 pixels per frame. This creates a 127-frame window where the point formula *will* produce negative values. While items do [despawn once their center Y coordinate is >487](https://github.com/nmlgc/ssg/blob/P0341/ssg/internal/Item.cpp#L104-L105), it makes little sense to attempt to narrow this window down to fewer frames:

1. Items only despawn after the collision check against VIVIT, giving them one additional frame below 487 pixels where VIVIT can collect them.
2. Items accelerate at a rate of 3/64 or 0.046875 pixels per frame, up to a maximum speed of 6 pixels per second. Since VIVIT will collect any item whose center Y position is 23.984375 pixels higher than her own, this seems to result in (487 + 6 + 23.984375) = 516.984375 as the earliest Y position where a respawning VIVIT could collect items, reducing the window to just the 32 frames where VIVIT is between 516.5 and 470 pixels.
3. But even with that limit in mind, stage scripts can (and do) spawn enemies far outside the bounds of the playfield, and shots and bombs can freely destroy them there.

Clearly though, we have to do *something* about this issue. But what, and how?

1. First of all, the 5×7-pixel font used for these popups does not define a minus sign sprite. The original %d format specifier did add a minus sign into the string, but the popup renderer simply skipped over any non-numeric character. These negative point item values have always been part of the game, but the lack of a visible minus sign made their popups blend in with regular positive ones. If it weren't for code analysis convincing me to change %d to %u, we might have never spotted this entire issue.
2. Secondly, the score displayed in the top-left corner of the playfield can only increase and never decrease. Negative score points therefore only really "exist" as part of the score delta, where they soak up points from other score sources until the delta gets positive again.

We could immediately reflect any negative deltas in the displayed total score:

However, that number isn't just some interim value, but represents the actual internal and official score that will be recorded in the High Score list, and consequently also in the future replay format. If there's any code path where the delta *doesn't* get fully added to the score before the game ends – such as [📝 at the end of TH04's Stage 6 and Extra](https://rec98.nmlgc.net/blog/2022-03-27)  – we'd end up with a different score than the same gameplay would have gotten on pbg's original build.  

	And sure enough, Shuusou Gyoku has the same issue. The delta is only ever fully added to the official score on a Game Over, and otherwise only gradually added as part of VIVIT's update function, in increments of [at most 100,000 points per frame](https://github.com/nmlgc/ssg/blob/P0341/ssg/internal/Maid.cpp#L57-L62). If we immediately committed any negative delta and a player quits after just having collected a point item with a negative value, the official score of that partial run would be lower than it would have been in the original game. This doesn't matter *right now* because Shuusou Gyoku doesn't enter scores into the High Score list if you quit a round, but it will matter once we start saving such partial runs as replays, which we obviously want to do. But even apart from that, it's ultimately just too minor of an issue to justify *any* change to the game's well-defined scoring aspects, or to newly introduce an inconsistency between displayed score and recorded score.

Hence, we're left with fixing just the rendering bug of the missing minus signs, which is easily fixed by repurposing one of the various 5×1 pixel lines in #DCDCFE from the system sprite sheet.

So, let's split Shuusou Gyoku's game logic into a library! Step 1, obviously:
Defining the scope of "game logic"
	On the one hand, the answer seems simple: [The `GameMove()` function neatly lists all subsystems that are involved in a frame of gameplay.](https://github.com/nmlgc/ssg/blob/P0326/GIAN07/GAMEMAIN.CPP#L1395-L1420) So let's take all of them, move them into a DLL, and then we're done, right? Well, there are several good reasons for not just taking this list of subsystems, and instead identifying and splitting off the actual *minimum* of gameplay-related code:

	Performance. We'd ideally use this isolated game logic core for mass validation of every new release against every replay ever created. The few unneeded subsystems might only add a couple of milliseconds per replay, but that will quickly add up at this scale.

	Thread safety, parallelism, and the associated refactoring effort. pbg stored most gameplay state in global variables, so we'd like to bundle all of it into a single C++ class that we can instantiate more than once. After all, [📝 process startup costs 30-40 ms on Windows](https://rec98.nmlgc.net/blog/2024-10-22#modules-2024-10-22), so it's much more preferable to multi-thread the replay validator instead. Minimizing the number of affected subsystems minimizes the amount of necessary refactoring work.  

	Also, how about [backwards seeking for replays](https://github.com/nmlgc/ssg/issues/62)? 👀 Said refactoring work would also lay the groundwork for the several "keyframe" snapshots of game data required for that feature to work at snappy frame rates. Might as well do it correctly now.

	If we place all logic code in the new `ssg/` directory and leave `GIAN07/` with only the presentational aspects, anyone working with this codebase can immediately tell that modifying code in `ssg/` runs the risk of forking gameplay and breaking existing replays. But the guidance and implicit documentation we gain from this physical separation can only be actually meaningful if we do make an effort to minimize the amount of code in `ssg/` and maximize the amount of freely moddable code and data in `GIAN07/`.

	While the game logic DLL will identify itself with the ReC98 release version number, I've also planned to hardcode a hash of all whitespace-stripped game logic source code. This hash will then be added to every replay as a second layer that can identify the game build a replay was recorded with. Hence, minimizing the amount of hashed code minimizes the chance for this identifying hash to change across versions or forks.

	Right at the top of `GameMove()`, you can see a call to `MWinMove()`, which processes the game's dialog boxes. Due to my [📝 new lazily-updated immediate-mode approach to text rendering](https://rec98.nmlgc.net/blog/2023-08-01#text-2023-08-01), each text box currently requires a dynamically allocated `std::string` to hold its exact contents. However, dialog also happens to be the only subsystem referenced in `GameMove()` that dynamically allocates during gameplay *at all*. If we can prove that this whole system doesn't affect game logic even with [our planned support for showing dialog in the new replay format](https://github.com/nmlgc/ssg/issues/36#issuecomment-3429282865), we now have a good reason for keeping it in the frontend. And since we *can* prove it, this goes most of the way towards the pretty bonus goal of reducing C/C++ standard library bloat (and thus, OS API dependencies) in this future DLL.

	And if we already don't want to include *one* subsystem, we might as well not include the *correct* number of subsystems.

	Map tiles are probably the most notable case of decorative data that remains exclusive to the frontend. Since VIVIT never cares what she's flying over, the new logic layer not only doesn't have to *process* them and their scrolling, but doesn't even have to bother *loading* and decompressing any per-stage map data. All it needs are the ECL and SCL scripts from `ENEMY.DAT`.

	That said, the game still throws a small wrench into my headless library plans. How does Shuusou Gyoku turn the Bonus and Evade points into these strings of individual letters I mentioned initially? Well, of course, by taking the most natural path offered by the C programming language:

sprintf(buf, "  Bonus    %7uPts", temp);
sprintf(buf, "%3d Evade  %7dPts", Viv.evade, Viv.evadesc);
Note how this also establishes an upper character limit for translations of these terms.

	And since every character (and even space) in the resulting string moves and draws from the RNG independently, this means that Shuusou Gyoku relies on a `sprintf()` implementation with standards-compliant length modifier support for replays to not desync. As mentioned above, I would have really wanted game logic to not overly rely on C standard library functions, and then it depends on the *one* function that has long been a theoretical thorn in my side anyway, due to all the unsightly locale bloat it pulls into the Windows binary.  

	Can't we get rid of `sprintf()` here, then? It's just two calls, after all. For the Evade string, we could easily get by without it, as the Evade counter and Evade score can't exceed the 3-digit 999 and the 7-digit 9,990,000. So we *could* simply provide a fixed-size static string and divide the individual digits into fixed offsets within this array. The `temp` variable in the Bonus string, however, can theoretically go up to…

Small bullets
((10,000 + (999 × 100)) × 600) +

Large bullets
((15,000 + (999 × 100)) × 1803)

	…273,104,700 points, which is 9 digits rather than the 7 allotted in the format string, and makes a manual approach considerably more awkward. Not to mention that the frontend also still uses `sprintf()` for all dynamic menu text, so it would still get linked into the main binary as long as I don't fully throw out MSVC's implementation.  

	Is all this locale bloat really *that* bad, though? Maybe my pursuit of purity isn't even worth it. Let's trace the chain of function calls down to the system APIs that Microsoft's `sprintf()` relies on:

`__stdio_common_vsprintf()`
`__crt_cached_ptd_host::__crt_cached_ptd_host(_locale_t)` with a `nullptr`,
which then initializes the PTD's locale pointer from `__acrt_initial_locale_pointers`.

`__scrt_initialize_crt()`

`__acrt_execute_initializers()`
`__acrt_initialize_multibyte()`, which calls [🚨 `FlsGetValue()`](https://learn.microsoft.com/en-us/windows/win32/api/fibersapi/nf-fibersapi-flsgetvalue) and [🚨 `FlsSetValue()`](https://learn.microsoft.com/en-us/windows/win32/api/fibersapi/nf-fibersapi-flssetvalue)

`_setmbcp_nolock()`, which calls [`IsValidCodePage()`](https://learn.microsoft.com/en-us/windows/win32/api/winnls/nf-winnls-isvalidcodepage) and [`GetCPInfo()`](https://learn.microsoft.com/en-us/windows/win32/api/winnls/nf-winnls-getcpinfo)

	On its own, this really doesn't look too bad or bloated. The 4 🚨-marked API calls aren't available on Windows 9x, but [📝 I already figured out how to deal with that last year](https://rec98.nmlgc.net/blog/2025-04-25#9xcompat-2025-04-25). The bigger problem, however, is what this means for my plans of building a beautiful freestanding game logic library with low Win32 API dependencies. C runtime initialization is all-or-nothing, and if I throw it out, I can no longer even use `sprintf()` because those CRT locale pointers remain uninitialized.

	On the one hand, I wouldn't have expected such a crusty old API to correctly decode UTF-16 surrogate pairs and convert them into a valid sequence of UTF-8 bytes without falling into the [CESU-8](https://en.wikipedia.org/wiki/CESU-8) trap. But was it really the best choice to make this conversion always fail with `errno == EILSEQ` on the first non-representable codepoint, instead of opting for *any* replacement character? And what's up with this codepage-dependent ASCII transliteration, where `ä` and `ö` get turned into `a` and `o` across the board, but `Ÿ` only gets turned into `Y` on CP1251 and is treated as invalid on CP932?

	Latin-1, but without the Ÿ? Nope, this is [something far worse](https://doxygen.reactos.org/da/d1d/wctomb_8cpp_source.html#l00077):
if(wchar > 255) {
	memset(destination, 0, destination_count);
	return ptd.get_errno().set(EILSEQ);
}
*destination = static_cast<char>(wchar);
	Under the `C` locale, these format specifiers simply take the first 256 Unicode codepoints, truncate them to 8 bits, and fail on everything else, producing a byte string in an encoding that is neither valid ASCII nor valid UTF-8. The resulting bytes do happen to match the original string when interpreted as CP1252 in this case, but only because [the last 75% of Unicode's Latin-1 Supplement block happen to match CP1252](https://en.wikipedia.org/w/index.php?title=Latin-1_Supplement&oldid=1371462427#Character_table) and the first two characters fall into exactly that range. This is also why the Ÿ vanishes – as we've seen above, Ÿ is `0x9F` in CP1252, but U+0178 in Unicode, so it fails the conversion. And if the UTF-16 string had contained any of the C1 control characters between U+0080 and U+009F inclusive, the resulting string wouldn't have been valid CP1252 either.

	This ridiculous non-encoding is not just a recent fallback path, but traces way back to Microsoft C/C++ 7.0 from 1992, whose C runtime featured Microsoft's very first and preliminary implementation of the underlying `wctomb()` function. Back then, Microsoft hadn't yet implemented locales into the CRT either, so this protected cast from `wchar_t` to `char` was *the only thing* the function did.  

	And in a tragic turn of events, [POSIX lawyers](https://inbox.sourceware.org/newlib/C6B0B594-6587-4D51-A894-9B265DF9B0AC@kba.biglobe.ne.jp/T/#u) can now claim that this preliminary hack from the Windows 3.0 days implements [section XBD §6.2 of the POSIX standard](https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/V1_chap06.html#tag_06_02):

[ISO C](https://cppreference.com/c/string/multibyte/wctomb) specifies that `wctomb()` should use the current locale, but leaves the locale's encoding unspecified.
But as of [2016's XBD/TC2/D4/0029 amendment](https://ieeexplore.ieee.org/document/7542098), [POSIX now specifies](https://stackoverflow.com/a/49857372) that the default `C` locale shall encode exactly 256 characters in some kind of single-byte encoding.
This encoding is not specified beyond the stipulation that the ASCII character set must appear somewhere. Implementations are free to map ASCII to any arbitrary codepoints, and then choose whatever other 128 characters they like to support.
Obviously, it is completely absurd to amend a fixed 256-character encoding into a *2016* standard just because [that's what the standard was always meant to say](https://pubs.opengroup.org/onlinepubs/9799919799/xrat/V4_xbd_chap01.html#tag_21_06_02). But POSIX is always right. 🤓
And after all, this behavior is useful because it guarantees lossless round-trip conversions between narrow and wide representations as long as wide strings only use these specific 256 characters!!1! 🤓

	Which leaves us with a state where both Microsoft and the POSIX police agree that this ancient code had better be kept around rather than removed. Backwards compatibility!  

	But I've seen enough. No modern C++ (and even C) program needs any of this. Even the pure optics of a freestanding game logic DLL are much more meaningful, and more than justify nuking Microsoft's `sprintf()` implementation across *all* of Shuusou Gyoku's code.  

	The replacement can come in one of three forms:

SDL offers a [`snprintf()`](https://wiki.libsdl.org/SDL3/SDL_snprintf), and we could abstract away the difference between it and the unsafe `sprintf()` used all over pbg's code. However, SDL only chooses its own no-nonsense implementation based on [build-time availability of `vsnprintf()`](https://github.com/libsdl-org/SDL/blob/e8262a87a7b51b8009a15ad7585bdf7b51efe5b8/src/stdlib/SDL_string.c#L1940-L1948) – which is probably a given for most pre-compiled SDL packages on Linux and gets us right back to the system-specific behavior we were trying to avoid for a core piece of game logic. Not to mention that the logic DLL should explicitly *not* depend on SDL.
Type-safe, modern C++ alternatives like [nanofmt](https://github.com/seanmiddleditch/nanofmt) are nice in theory, but highly disruptive in how they require a rewrite for every `sprintf()` call site. Also, code generation is highly disappointing, and we'd still need a solution for miniaudio's logger, which uses `sprintf()` as well.
Fortunately, there are plenty of minimal and no-nonsense `sprintf()` implementations out there that can work as drop-in replacements. [eyalroz/printf](https://github.com/eyalroz/printf) ticks all the boxes, is actively maintained, and comes in at a very pretty 3.5 KiB of compiled code size in its most minimal configuration. Redirecting miniaudio to that implementation still requires [silly header inclusion hacks](https://github.com/nmlgc/ssg/blob/P0341/hatoyama/engine/miniaudio/miniaudio.c) though… Sigh, I want this library gone from this codebase so much.

	With MSVC's `sprintf()` implementation gone, we should now be able to safely bypass the C runtime initialization before `DllMain()`, avoid the bloat it would pull into the binary, and end up with a completely freestanding `ssg.v1.005.dll` without any system dependencies:
#pragma comment(linker, "/ENTRY:DllMainCRTStartup")

int __stdcall DllMainCRTStartup(void *, uint32_t, void *)
{
	return 1;
}
	Yes, that's all the magic. `/NODEFAULTLIB` would make things a lot harder.

	That only leaves us with two more linker errors:

error LNK2001: unresolved external symbol ___CxxFrameHandler3
error LNK2001: unresolved external symbol ___std_terminate

	Sigh again. Time to also take a close look at…
C++ exception handling on MSVC
	…and finally learn what all the related compiler warnings and flags actually mean. It starts with [one thing](https://learn.microsoft.com/en-us/cpp/error-messages/compiler-warnings/compiler-warning-level-1-c4530):
warning C4530: C++ exception handler used, but unwind semantics are not enabled. Specify /EHsc
	This warning originates from the few [hilarious instances where pbg used exceptions for control flow](https://github.com/nmlgc/ssg/commit/3b3a88e84ce405d470ea0a13e22ee4eb0e0ed409). After rewriting them, we *should* be able to drop `/EHsc` again and be good…  

	…except for the fact that [📝 we've migrated to C++ Standard Library Modules](https://rec98.nmlgc.net/blog/2024-10-22#modules-2024-10-22) two years ago. Creating these modules requires compiling the entire C++ standard library upfront, and Microsoft's implementation is free to throw and catch internally wherever it wants. If we remove `/EHsc` from the module compilation command line, we don't have to wait long before we encounter the first case of C4530 in the alphabet, emitted for `<chrono>`'s [`get_tzdb_list()`](https://github.com/microsoft/STL/blob/94aef91ebec9e6e3fd9302840e657b09e536d90d/stl/inc/chrono#L2420).

	OK, but the fact that *some* standard library functions might throw and catch exceptions should not have any impact on *our* code. So let's try a mixed approach: Compiling the standard library with `/EHsc`, but removing the flag for our own code. Well…
warning C5050: Possible incompatible environment while importing module 'std.compat': _CPPUNWIND is defined in module command line and not in current command line
	Which we now get for every translation unit in the codebase. This warning is much worse than the other one: C4530 always points at a specific exception handler, but C5050 just points at the `import` and complains about a macro mismatch, breaking down the difference between activated and deactivated unwind semantics to a single preprocessor macro. Does this macro matter? How can we possibly say whether it does or doesn't?

	So let's take a step back to C4530 and that initial module compilation. On the one hand, we'd fully expect to run into *some* restrictions if we wanted to code completely without bothering about C++ exceptions. But if we simply don't use any of these functions where MSVC emits C4530, we should be good, right? After all, C4530 defaults to just being a warning, not an error.  

	On the other hand, I do use plenty of `std::vector`s across the frontend, and those certainly do throw in quite a few of their methods. The game logic DLL obviously shouldn't use `std::vector`, but I definitely don't want to have two compiled standard library modules with different exception handler settings in my build tree. But wouldn't ignoring that warning just introduce yet another bit of uncertainty?

	Well, not quite! As the diagnostic says, `/EHsc` is all about *unwinding the stack* in case of an exception – i.e., running the destructors of any local objects in scope while moving up the call stack to find a handler for that specific exception. And nothing else – you can still throw or catch exceptions just fine, but you just might leak memory or resources if you do.  

	But that also means that `/EHsc` doesn't matter as long as you never `catch` anywhere. In that case, your program *will* terminate whenever it throws an exception because there's no handler. You might expect one final round of stack unwinding before termination, but [the C++ standard also leaves that up to implementations](https://eel.is/c++draft/except.terminate#2), justifying it by claiming that [enforcing it makes life harder for debugger writers](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/1995/N0597.asc).

	That answers the question for our own code. But aren't we getting C4530 for standard library code that *does* catch an exception? Let's experiment with a feature where catching exceptions is crucial to its intended behavior, and where we can trigger it more easily than by occupying all memory:
import std;
#include <stdio.h> // `std::cout` could also throw, lol

struct Inner {
	~Inner() {
		puts("Inner destroyed");
	}
};

int main()
{
	// `std::packaged_task` stores the return value or exception of the callable
	// it's initialized with. This obviously requires an exception handler
	// inside the standard library, and therefore makes a good test case for
	// `/EHsc`.
	std::packaged_task<void()> task([] {
		Inner instance;
		throw "from task";
	});
	task(); // Run the task

	// `#define try` can skip exception handling here
	try {
		puts("Rethrowing exception");
		task.get_future().get();
	}
#ifndef try
	catch (const char *error) {
		printf("Caught exception %s\n", error);
	}
#endif
	puts("Returning");
	return 0;
}
	And compile it with every permutation of `/EHsc` at `std` module level and source level, as well as with the final handler removed:

Warnings for source file

	Amazing how C++ modules are still bleeding-edge enough to crash compilers, a full two C++ standard versions after they were introduced! Those weren't the only Internal Compiler Errors I've seen in this development cycle either, not by a long shot…  

	Regardless, these results are even better than I would have expected:

`/EHsc` and, by extension, C4530, don't seem to matter at all during module compilation. Any `/EHsc` setting on the module-importing source file seems to re-activate stack unwinding for any standard library code.

	Why is that the case? Because neither `std.ifc` (the [Built Module Interface file](https://en.wikipedia.org/wiki/Modules_(C%2B%2B))) nor `std.obj` (the compiled object file you're supposed to add to your link command line) *actually contain any pre-compiled code*. While it's clear that the IFC contains some sort of binary representation of the parsed and analyzed code, you might think that at least *some* pre-compiled code ends up in the .obj. But no, it only contains all static *data* referenced by the standard library. In fact, it can only *ever* contain data because all code in the `std` module comes from headers and therefore has to either be templated or declared as `inline` to maintain the [One Definition Rule](https://en.wikipedia.org/wiki/One_Definition_Rule). Thus, the binary representations from the IFC file only get instantiated and specialized in each translation unit they're imported into, under that unit's exception handling rules. MSVC's frontend probably emits C4530 in a much too early analysis stage, way before the absence of `/EHsc` would actually matter.  

	(And yes, the IFC does reference plenty of precompiled code, but all of that code is part of MSVC's runtime libraries.)

	The only critical case is the very first one, where we do `catch` without `/EHsc`, and therefore skip running destructors you would expect to be running. In this case, however, MSVC emits C4530 *precisely to protect us from this exact issue*. This specificity shoots C4530 right up there towards GCC's [📝 `-Wformat-overflow`](https://rec98.nmlgc.net/blog/2025-10-19) as one of the best diagnostics ever emitted by a C++ compiler.

	Because we can now derive a rock-solid strategy: Disable C4530 during module compilation, but treat it as an error on all other build command lines. This allows us to safely compile everything without `/EHsc`, because we'd now get a compile error as soon as we write code where the absence of `/EHsc` would matter.

	And as a nice bonus, MSVC can now properly optimize DLL-exported class constructors as it no longer has to accommodate exceptions flying across DLL boundaries.

	So, we got pretty far, but in the end, did all this bloat reduction really matter? Absolutely, if you ask me:

![Screenshot of Dependency Walker running on Windows 98 and displaying the new Shuusou Gyoku game logic DLL, showing off its three minimal imports of GetProcessHeap(), HeapAlloc(), and HeapFree() as well as its 73,216-byte size.](https://rec98.nmlgc.net/blog/static/2026-10-05-ssg.v1.005.dll-Dependency-Walker-Windows-98.webp?1e47d34e)
And all of these three imports come from our own memory management code. Not removing C runtime initialization would have bloated the DLL to 157,184 bytes – more than twice the size it ended up being.

	We've learned something about two unfortunate aspects of the C and C++ standard libraries, got rewarded with a beautiful, small, and freestanding binary that natively runs on every Windows version since 95, and we didn't even have to screw around *that* much to make it happen, despite still compiling with current Visual Studio. When I went into this, I assumed that we'd have to use `/NODEFAULTLIB` and link to at least [SDL's C runtime polyfills](https://github.com/libsdl-org/SDL/blob/main/src/stdlib/SDL_mslibc.c), but we didn't even have to do that. Instead, the DLL still gets to use [security cookies](https://learn.microsoft.com/en-us/cpp/build/reference/gs-buffer-security-check?view=msvc-170), MSVC's built-in functions for 64-bit math on 32-bit x86, and a wide range of modern C++ standard library features, including `std::unique_ptr` with adopted raw pointers and custom deleters, ranges and views, spans, and `std::invoke`.

	Alright, I'm happy with the build quality, so on we go to Step 2 of the actual mission:
Completing the separation of game logic
	Which certainly was the most grueling part of this development cycle. Even *round initialization* required a good part of a full push just to clean up the code and end up with a consistent API that works for regular 6-stage rounds, Extra Stage rounds, replays, and the pre-recorded demos. This codebase is truly cursed: You take a look at a new piece of code, notice that it's a mess of procedural state mutations, and just *have* to streamline it before you even want to touch anything. 😩

	So, how do we get to our single `C_SSG` class that bundles all game state and offers a central method to run a frame of gameplay based on player input? If we want to keep code changes to a minimum and not basically rearchitect the entire game from scratch, there are two realistic paths from the code's original bunch of globals and functions:

Throw all gameplay state and functions into a single class. This would remove quite a few header files, but the .CPP files would stay largely identical, mostly only requiring changes to the function definition headers from free-function to class method syntax:
	-void fragment_move(void)
+void C_SSG::fragment_move(void)

	On the other hand, we'd then have a god object, and every change to its class declaration would trigger a recompilation of every .CPP file in the logic DLL.
Retain the code's original subsystem separation, turn each subsystem into its own class, and restrict the possibilities for rampant state mutation by only giving each subsystem the references to the other subsystems it actually needs. A few of these references can then even be `const`, providing additional safety and documentation of intent. `C_SSG` then bundles all of these smaller classes and acts as [a giant switchboard connecting all the subclasses to each other](https://github.com/nmlgc/ssg/blob/P0341/ssg/internal/SSG.cpp#L24-L68). This maintains the game's existing code structure at the cost of hundreds of lines of reference management boilerplate. We do get to make good use of forward declarations to keep header dependencies to a minimum, though.

	Initially, I gravitated towards option 1), but immediately disliked it mere minutes after I started typing. So, one class per subsystem it is. This is slightly more disruptive to the .CPP files in how we get an extra change to each function call between subsystems, but those are trivial to review. In most cases, it's just an additional dot accessor between two camel-cased words.  

	But yeah, this only retains the original file layout in spirit as well. Once I was done, I immediately regretted *that* solution too. We might have avoided unneeded recompilations of *logic* translation units, but the whole nature of this split still required moving all game state rendering code to another place. And since it didn't really make sense to have one tiny source file per rendered subsystem, I went with [a single giant one](https://github.com/nmlgc/ssg/blob/P0341/GIAN07/GameDraw.cpp)…

	And just in case you're wondering how large `C_SSG` ended up being in the end: 403,616 bytes on 32-bit systems, and 405,984 bytes on 64-bit systems.

	I did have to make a few more interesting implementation decisions as part of this whole logic/presentation split and the resulting API:

	You might have already noticed it from the `KERNEL32.DLL` import list above, but yes, I decided to not add any file I/O to the game logic DLL. It made much more sense to leave that to whatever language the DLL is used from: The high-level file I/O functions of such languages are typically more convenient to use, and often provide far superior error handling than whatever I could cobble together across a FFI boundary.  

	However, the DLL does take care of transparently decompressing packfiles and allocating the ECL, SCL, and replay buffers managed as part of each gameplay instance. In fact, this is exactly where the three Win32 heap management functions come in. This breaks down replay initialization to a short sequence of steps that involve passing the raw contents of `ENEMY.DAT` and the replay file as borrowed buffers into the `C_SSG` instance and then loading the necessary scripts by passing the stage number. But since [jwilins' raw asset loading fork](https://github.com/jwilins/ssg_raw) also exists and I do in fact endorse it for experimental use cases, I've also added a variant that bypasses the packfile and [takes raw ECL and SCL buffers](https://github.com/nmlgc/ssg/blob/P0341/ssg/internal/SSG.hpp#L82-L87).

	Speaking of FFI usage, this was another key design goal of this library. After all, we'd ultimately like this code to perform replay validation on [Silent Selene's server](https://github.com/n-rook/thscoreboard/issues/505), which is written in Python. It also stores replays in a PostgreSQL database, so it will certainly appreciate not having to write out replays to the file system before being able to pass them to game logic code.  

	Without a specific developed use case, it didn't make all too much sense to spend time on full-fledged feature parity for the FFI just yet. And so, running and inspecting a replay remains C++-exclusive for now. But I at least started by ensuring, at build time, that all intentionally public headers and all of pbg's original gameplay structures are valid C code. This way, you can already feed them to all kinds of automated binding generators.

	For the most part, the separation of logic and presentation continues to work as it did with the original code's split between `GameMove()` and `GameDraw()`: The logic layer runs one frame of gameplay, and the frontend's renderer can then take the resulting state and draw it. However, there are still several events that can happen in the middle of a frame, triggered by conditions and with parameters you couldn't pull from game state at the end of the frame. Sound effects are the most obvious example, but these kinds of events would also need to occur for the majority of SCL instructions, including all kinds of background effects and the entirety of the in-game dialog system. I could have put all of these events into some kind of queue to be processed at the end of a frame, but that would have required allocations and introduced a whole new problem of needing to snapshot a whole lot of data at the time of the event, just to ensure that we fully match the original game's behavior. So, [classic hooks via C function pointers](https://github.com/nmlgc/ssg/blob/P0341/ssg/Hook.h) it is.  

	Since we also need to cover three specific ECL instructions for certain visual effects and, ideally, [pbg's existing debug tracer](https://github.com/nmlgc/ssg/blob/P0341/GIAN07/ECLFront.cpp#L52-L130), I went for full-on per-instruction ECL and SCL hooks. In theory, you could use these hooks to even write a full debugger on top of the game logic library. For ECL, though, you'd have to [explicitly opt into receiving hooks for every single instruction](https://github.com/nmlgc/ssg/blob/P0341/GIAN07/LogicInstance.cpp#L40-L42). The Extra Stage processes roughly 200,000 ECL instructions throughout the 7 minutes of a full run, which doesn't bode well for certain languages where C function pointers would have to cross expensive FFI boundaries. SCL instructions are hooked unconditionally, as they are far less numerous.

	And since it doesn't really fit anywhere else: Obviously, the Linux version also gets a `libssg.so.1.v1.005`, together with the version-less linker-name and versioned SONAME variants as per [the usual shared library conventions](https://dwheeler.com/program-library/Program-Library-HOWTO/x36.html). Usually, the latter two would form a symlink chain that ultimately points to the real shared object containing the actual code. Unfortunately though, this naive approach would really degrade build performance under Tup in particular. Despite Tup's Unix-centric origin, Tupfiles *really* prefer the Windows approach of a separate import .lib file that defines the API surface of a DLL. If we then use [the `^o^` flag](https://gittup.org/tup/manual.html#lbAI) in the DLL's link rule and build a new version of that DLL, Tup can then skip needlessly re-linking any dependent binaries if the newly created import .lib is exactly identical to the old one. On Linux, though, the final target behind `libssg.so` (which is what linkers read when you specify `-lssg`) is essentially different on every code change, triggering a rebuild of every dependent binary and thus kind of defeating a big point of shared libraries.  

	Unix linkers don't produce a direct equivalent to Windows .lib files, but it's still possible to derive a .lib-equivalent code-less .so dummy from a regular full .so file. All it needs is some `nm` and `sed` magic to produce a stable piece of ASM source that we can then link into a regular, non-symlink `libssg.so`. 🧙 Then, linkers (and *only* linkers) will never actually look at the full .so file containing the actual code, and we get to also use the `^o^` flag to reproduce the same developer experience on Linux. Check out [the respective tupblocks commit](https://github.com/nmlgc/tupblocks/commit/0694ec53854f24a1a9860a41022a6fe01027cc7) if you're interested in the specifics.

	One hidden change concerns the game's debug mode. pbg's original code had a debug option to turn off collision detection, which he implemented by [conditionally returning from the "VIVIT got hit" function based on a debug-exclusive flag](https://github.com/nmlgc/ssg/blob/pbg/GIAN07/MAID.CPP#L422-L424). Unfortunately, this kind of debug feature creates massive conceptual problems for what we're trying to do here:

Since our library should be able to process multiple game states in parallel, this should no longer be a global flag. CLI and logic API users should not have to split replays into two batches based on whether the flag was set or not. Thus, this must be another [round parameter](https://github.com/nmlgc/ssg/blob/P0341/ssg/Round.h#L29-L38).
However, the fact that this *wasn't* a proper round parameter also means that the flag wasn't propagated into pbg's old replay format *at all*. Hence, it's already impossible to identify existing replays recorded with the `Hit` option turned `[O F F]` from their header data alone. The CLI will *help* identify such replays (since running them with collision detection enabled is likely to cause a desync at *some* point), but it can't definitively tell either.
But if the replays don't contain this flag, who sets it? Well, it would continue to be passed from the frontend – i.e., the game *and* the replay CLI, introducing one more command-line option to the latter. And then we're right back to where we started, forcing users to manually track a replay-specific property as part of the simulation environment.
We could start tracking that flag from now on, [repurposing one of the various unused bits in pbg's replay header](https://github.com/nmlgc/ssg/blob/pbg/GIAN07/GIAN.H#L152-L176). But should we really open a door for cheaters by having such a round parameter in the first place?
We could continue limiting this feature to debug builds. But do we really want to continue having separate behavior between Debug and Release builds, and add separate API contracts on top? 😵

	That's way too many questions without easy answers for a minor debug feature that non-developers won't ever even encounter. Just removing it seems to be the easiest way forward, but on the other hand, this kind of feature *is* vital for debugging. ![:thonk:](https://rec98.nmlgc.net/static/emoji-thonk.png?0a583f91)  

	So I chose to replace it with a different approach to invincibility that doesn't affect game logic: Simply starting each round with 252 lives. Why 252, and not the 255 you'd expect from the unsigned 8-bit integer we obviously assign to? Because the game spawns 3 extend items across its 6 stages and pbg doesn't clamp lives to any maximum value. 252 lives are plenty for clearing both a regular 6-stage run and the Extra Stage without moving, *and* allow you to still pull off a no-miss run that collects all 3 extends without the life counter rolling over to 0.  

	Since this new feature merely overrides the initial `PlayerStock` value, which is directly stored in replays, we end up with a much more sustainable debugging feature. New debug replays recorded with this feature enabled remain compatible with even pbg's original release of Shuusou Gyoku, and replay hosters can identify them just as easily as if I had picked some previously unused bit in the header to indicate the old flag. Maybe they don't even have to check at all, since the `PlayerStock` number is a regular configuration option that the UI can just prominently display.

	Maybe, we can even restore the original feature once we have that new extensible replay format and have implemented all the required bureaucracy for the highly requested [quirk toggle](https://github.com/nmlgc/ssg/issues/38). That would already create at least one replay-incompatible gameplay fork, after all. But for now, this is what we're going with.

![Screenshot of Shuusou Gyoku's Config → Difficulty menu in pbg's Debug mode, activated by #defining the PBG_DEBUG preprocessor macro, as shown in pbg's original code and all ReC98 builds until P0326. The cursor highlights the Hit option turned [O F F\], which deactivates collision detection.](https://rec98.nmlgc.net/blog/static/2026-10-05-SH01-DebugMode-P0326-Hit-OFF.webp?c316cd06)![Screenshot of Shuusou Gyoku's Config → Difficulty menu in pbg's Debug mode, activated by #defining the PBG_DEBUG preprocessor macro, as shown in the ReC98 P0341 build. Note the flipped menu logic: With the original `Hit` feature, the `[O F F]` choice opted into nonstandard gameplay, while the `252Lives` feature only overrides the `PlayerStock` when turned `[O N]`. The negation here is purely visual, and existing `秋霜DBG.DAT` files will automatically use the matching behavior.

	Now that the codebase has to produce two more binaries than it did before, I also had to reconsider the physical layout of the repo, and how to best share any code that needs to be shared between any of these binaries.  

	Ever since I started work on Shuusou Gyoku, I made a conscious effort to physically separate generic engine and platform code from game-specific code. Initially, I went for the most logical and terse layout from the point of view of my build system: The various subdirectories of the `platform/` directory contained all platform-specific backend code, while `game/` contained everything else that applied to all platforms. This kept the Tupfiles simple, as I only needed a few specific globs to list all files that should go into a platform's respective binary. A few [cracks](https://github.com/nmlgc/ssg/blob/P0326/Tupfile.win32.lua#L114-L119) and [exceptions](https://github.com/nmlgc/ssg/blob/P0326/Tupfile.linux.lua#L34-L36) started to emerge over the years, but the overall layout idea generally worked out well…  

	…except that it didn't really matter *what* I did as long as all code went into just one binary. But now that we add two more, we really don't want to link all that code into all three binaries and rely on the linker to eliminate whatever isn't needed. All these unneeded dependencies would end up forming a somewhat triangular-looking build graph that reduces Tup's throughput and triggers unnecessary rebuilds during development. And we *especially* don't want to force replay servers to [install all these development packages](https://github.com/nmlgc/ssg/blob/882bdc1dd640fcf24d8dac75e1f03b8fea810985/build_linux.sh#L25-L32) if all they need to compile is the game logic .so binary.

	And so, the completed feature ended up calling for the game-independent code to be modularized along a total of four different axes:

A *logic* layer that provides a few small bits of code on top of the C++ standard library module, provides eyalroz's printf library, and adds no further dependencies. Since it mostly defines types, classes, and templates, and comprises very few translation units on its own, it's small enough to get statically linked into all three binaries.
An *app* layer that contains all the helpers on top of SDL that we want to use in both the game and the replay CLI, as well as the SDL dependency itself.
An *API* layer. This one currently only contains functions to retrieve game logic and ReC98 build version strings. Only exists because I needed an additional game-independent layer that gets linked into the game logic DLL but *not* into the CLI or game binary, since they should always pull these versions from the DLL.
And finally, an *engine* layer that gets all the remaining code required for the main audio-visual gaming experience. This layer also bundles all remaining third-party dependencies such as libogg/libvorbis, dr_flac, libwebp, and miniaudio.

A replay validation CLI
Usage: ssg_cli [OPTIONS] replay_file [replay_file...]

Options:
  -d, --dat <ENEMY.DAT>  Custom path to the game data archive
  -h, --help             Print this usage text
  -q, --quiet            Only report replays that don't simulate completely
  -v, --version          Print version info

`replay_file` can contain `?` and `*` wildcards.
If `-d`/`--dat` is omitted, game data will be taken from `C:\path\to\ssg\ENEMY.DAT`.
Yes, that's single-level globbing for all operating systems. Works with relative paths, absolute paths, and UNC network paths!

	Correctly initializing replays in such a CLI posed a final slight challenge. Since pbg's single-stage replay format doesn't actually store the stage in its header, we can only possibly derive a replay's stage from its filename. We could just enforce the same `秋霜りぷ*.DAT` filename scheme that the original game's replay menu expects, but that idea quickly fell apart in the face of even my current existing Shuusou Gyoku replay collection, which features multiple descriptively named replays for every stage. I'd obviously prefer to analyze the whole set with a single `*` glob.  

	Keeping in mind that you'd have to trim any descriptive text if you want to view these replays in-game, it made sense to go for a small algorithm that considered only the one part of such filenames that you'd keep unchanged for easy renaming. And so, the resulting algorithm simply looks for the `秋霜りぷ` prefix and then detects the stage from a subsequent `1-6` or `Ex` string. This way, any descriptive extra text can freely include `1-6` or `Ex`, and can be placed before the `.DAT` extension, after the extension, or even at the beginning of the file name. The algorithm can then also support several mojibake versions of that prefix, which currently include the `‘š‚è‚Õ` string you'd get on CP1252, and the four underscores (`____`) you'd get on Western Windows 98.

	This need to handle Unicode filenames also brings us to what might seem like one of those typical strange ReC98 engineering decisions. The `app/` layer's dependency on SDL might have already given away that I chose to write this CLI entirely on top of SDL's standard library and logging functions. Typically, you wouldn't consider using a low-level game library for a CLI tool, but there are several good reasons for SDL in particular:

	Unicode command-line arguments just work without me having to write a single line of platform-specific code. That feature is obviously crucial given the filenames this tool usually needs to process. It sure is nice that I don't have to [solve the same problems all over again](https://github.com/thpatch/win32_utf8/commit/109686e3a566fb2f2d52c51bf3ebb6b153ba452a).

	Same for Unicode console output on Windows. The only platform-specific code we actually need stems from SDL's unfortunate choice of outputting to `stderr` rather than `stdout`, requiring [a few slightly ugly lines of code](https://github.com/nmlgc/ssg/blob/P0341/hatoyama/app/replay_cli.hpp#L218-L223).

	Thanks to [`SDL_GlobDirectory()`](https://wiki.libsdl.org/SDL3/SDL_GlobDirectory), cross-platform globbing support for systems without powerful shells was a quick and cheap addition. We might even get [recursive globbing via `**`](https://github.com/libsdl-org/SDL/issues/11340) as soon as someone sends a PR. The enforced separation of path and filename parameters slightly complicates the usage of this function, but [it's actually not too bad](https://github.com/nmlgc/ssg/blob/P0341/hatoyama/app/replay_cli.hpp#L287-L307). Certainly much simpler than sticking to the C++ standard library, which would require [approximating globs by converting them to regexes and matching all files by hand](https://en.wikipedia.org/w/index.php?title=Glob_(programming)&oldid=1374712146#Other_implementations).

	SDL is part of all Windows and Linux packages anyway.

	Ultimately, this CLI is meant to serve two goals: A general demonstration of the fact that Shuusou Gyoku's game logic now has a headless API, and a tool that will ultimately facilitate mass validation of every replay ever recorded, as part of my release pipeline. Depending on how I'm going to approach validation, I may or may not add support for a more machine-readable output format. Regardless, the CLI is meant to demonstrate the API, not the other way round.

	If you remove all the argument parsing and globbing code, you're left with roughly 60 lines of C++ code that use the DLL's API for loading `ENEMY.DAT` and the replay, and looping over every frame. And that's *with* error handling at every step of the way. Shelling out to the CLI and parsing its output probably takes more code than just calling the same C API of the game logic DLL from your programming language of choice. And given the months of work that went into boiling down this API into only its most elementary steps, it's likely to remain stable for quite a while.  

	(There will certainly be more hooks, though. Make sure to use proper binding generators if necessary for your language of choice!)

	Since almost everything in the CLI is a call to either an SDL or logic DLL function, I can remove the C++ runtime initialization on Windows at, once again, little additional cost, and end up with a 9 KiB binary! I might assign way too much importance to these optics, but I love how this clearly communicates that the CLI contains no additional magic whatsoever, even if you don't read its source code.

	Even with the Hatoyama split, I had to cut a few minor corners to get this feature out the door at all within the funding it received:

Talking about MASM/TLINK-style toolchains conflates assemblers and linkers. These are separate types of tools and handle this piece of code very differently, not to mention that they come from two different vendors.
TLINK only sees assembled .OBJ files, and the `EXTDEF` record of the OMF format does not even store the type of the pointed-to symbol. Thus, there can't be any symbol-type mismatch error at link time.

But aside from that: The bot already realized that the code only uses the address of the symbol via `seg` and `offset`, and no instruction dereferences the values behind the pointed-to symbol. Hence, the pedantically correct suggestion would be `EXTRN _SolidTile`, without any indicated pointed-to type, which is the equivalent of a `void *` in C.
