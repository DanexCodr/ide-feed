[About a year ago](https://ericswpark.com/blog/2025/2025-04-18-a-rant-about-cheap-proprietary-ip-cameras-featuring-hej-home/), I ranted about this particular cheap IP camera that was
based on some proprietary Chinese IoT platform named Tuya. After trying and
failing to get a local video stream from it without going through their servers,
I concluded that my time would be better served by using cameras that actually
exposed their streaming capabilities, and set it aside.

Well, I recently dug the camera out while moving to my new job in New Jersey,
and thought it might be worthwhile to give it another shot. I had plenty of
spare time, and if I couldn’t figure it out, LLMs are recently all the rage for
being really great at reverse-engineering things. But my initial goal was,
I’d attempt it myself first, and then hand it off to an LLM if I failed and try
and learn something from what it had figured out.

So what’s our goal, exactly? We know from last time that the camera has some
sort of ONVIF server built in. That’s basically a standardized interface for
IP cameras, defined by the Open Network Vision Interface Forum (or ONVIF!)
And most ONVIF cameras expose their video streams using RTSP, or the
Real-Time Streaming Protocol. You may have come across this protocol if you’ve
ever streamed to a live-streaming platform like YouTube or Twitch.

The problem is that these servers are disabled on the firmware side, and their
ports are closed off. Last time, we tried to enable them using the configuration
options, but that didn’t work. Now, it’s time to figure out why that failed, and
if there’s truly a way to enable those streams.

So with that in mind, let’s first extract the firmware image with `binwalk -Me`:

| Decimal | Hexadecimal | Description |
| --- | --- | --- |
| 113992 | 0x1BD48 | CRC32 polynomial table, little endian |

OK, so it runs Linux 3.4.35. When was that released again? March 2013.
A 13-year old kernel! (I guess it was only 8-years old when they compiled it.)

Last time, we found the Tuya configuration file with the ONVIF config at
`./extractions/cctv.bin.extracted/760CCC/jffs2-root/tuya_config.json`. I think
the reason it might not have worked is because we edited the firmware image
itself with a hex editor, and doing so probably corrupted some checksum.

But, we have the image extraction, so why not trace where the config option
is being used? Perhaps the binary doesn’t even use that option at all.

So what binary is launched? We should look at the initialization script of the
camera at `.\extractions\cctv.bin.extracted\370000\initrun.sh`. That script
extracts some app tarball, then runs the script at `home/init.d/initS`, which
in turn runs the other init scripts inside `home/init.d`.

Most of the scripts are like, setting up the kernel parameters regarding memory
and networking and DHCP and what not, so we’ll skip past all that. The important
bit is the last script, which is `S60ppsapp`, which runs `ppsapp` in `/home/app`.

One `find` command and we find
`extractions\cctv.bin.extracted\370000\app.tar.gz.extracted\0\decompressed.bin.extracted\0\home\app\ppsapp`.
And `strings` tells us it has ONVIF stuff in it:

```
$ strings ppsapp | grep -C 2 "onvif_enable"
motion_area_switch
motion_area
onvif_enable
onvif_pwd
```

OK, but is there some reference to the ONVIF streaming within the binary itself?

```
$ strings ppsapp | grep "Starting onvif"
Starting onvif server on port %s
$ strings ppsapp | grep "rtsp://"
rtsp://
rtsp://%s:%d/Streaming/Channels/101
rtsp://%s:%d/Streaming/Channels/102
```

OK, that’s good! We now know the ONVIF streaming URL format, though we still
need to know what port it runs on.

So let’s throw the binary itself into Ghidra and run the analyzer. Looking
through the strings, a lot of the hardcoded paths reference
`/var/lib/jenkins/workspace/`, so whoever built this image probably did so with
a Jenkins pipeline. Does it really matter for what we’re doing? No, but I
thought it was interesting. They probably have a Jenkins workflow for each
camera SKU they push out the door, although I’m sure they use it only once,
considering that support is an afterthought.

The binary itself is 2.4 MB, and I’m not that familiar
with reading ARM assembly, but we don’t have to, just yet! We just need to look around
for the onvif part since we know the config string there.

On Ghidra, strings can be found by going to “Search -> For Strings…”. After
you select the options the string search window shows up. Luckily for me,
filtering for `onvif_enable` shows only two places where they are used:

But why didn’t the hex-edit work? Well, [JFFS2 is a special filesystem](https://en.wikipedia.org/wiki/JFFS2) that
is log-structured, and it’s designed for flash memory devices. I guess it’s
sorta like F2FS, which is another filesystem designed for flash memory devices,
but unlike its usage on Android devices JFFS2 is designed for flash memory that
doesn’t have a wear-leveling mechanism on the hardware side.

**What is wear-leveling?** TL;DR: Flash chips and SSDs have flash cells. Flash
cells have a limited lifespan and don’t like it when you write to them
repeatedly. Wear-leveling mechanisms thus try and make sure writes are evenly
distributed across flash cells to prolong their lifespan.

Because flash memory can only be addressed in terms of blocks, and because JFFS2
has to handle the wear-leveling mechanism in software, you can’t just overwrite
the old block when you change one byte in it (in this case the config option),
because you’re then writing to that same spot in memory. JFFS2 thus writes
another block to the flash memory with a higher version number.

And like all good filesystems, [JFFS2 utilizes checksums for error detection](http://linux-mtd.infradead.org/~dwmw2/jffs2),
and from what I can gather, uses a 32-bit CRC. Which means editing just the data
portion corrupts that entire block.

Now, I don’t remember if I changed all of the occurrences of `onvif_enable` last
time or not, but it doesn’t really matter. If a given block is bad, JFFS2 will
go back to the older block with a lower version number. And if I did change
all the blocks and corrupted them, I’m assuming the `ppsapp` binary then fell
back to sane system defaults, which was probably why I got the chime during
boot.

The ONVIF HTTP handler is `FUN_0007893c` (vaddr `0x7893c`). Before it parses or answers any request, it does this:`if (*ONVIF_ENABLED_1 != 0) {
   if (FUN_00019f50c() != 0) {
       return;              // <-- silently drops the request
   }
   if (event != 0x64) return;
   ... handle HTTP / ONVIF ...
}``FUN_00019f50c` reads a global network/cloud state at `0x344230` and returns nonzero for states **1, 2, and 4**:
`0` → proceed
`1` → blocked
`2` → blocked
`3` → proceed
`4` → blocked
`5` → proceed
That state is maintained by a Tuya SDK network-monitor task (`FUN_00019fbcc` → `FUN_00019fa4c`) driven by the Wi-Fi and cloud-status callbacks. With internet blocked, the camera can get an IP and listen on 8000, but it never transitions to a “ready” state — so the handler returns before sending a single byte.

# Conclusion

I learned a **lot** attempting this. But at the same time, the ending might not
be quite so satisfying.

On one hand, it feels like I used LLMs as a crutch, because I’m not yet skilled
at reading ARM assembly and actually going through the motions of reverse
engineering binaries by hand through Ghidra.

On the other hand, I still learned a lot by actually going through the motions
of decompressing, searching, soldering, packaging, compressing, flashing, and
the large amount of research and time that went into this. I actually started
this blog post in the second week of September! Even though I was quite busy
with work at the same time, the roughly two months of work didn’t seem wasteful.

I also think that it’s cool that LLMs are making this more accessible, and even
though it brings the temptation where you just offload everything to it and have
it do all the patching and re-compressing for you to have a perfect working
binary firmware image at the end (because yes, I’m sure it could definitely do
that now), making sure that you **don’t** do that and go through the
intermediary steps that you know how to do yourself really helps.

Also, for those that are curious: the total cost of running the Deepseek model
on OpenRouter was 22 cents. Yes, **$0.22**. You don’t need an expensive
subscription or sell your soul to Altman or Amodei.

Would I try this again? Not for this particular class of camera. As I said in
the previous post, this was basically an e-waste camera that a relative of mine
gave me for free, and we all know by now to not buy any crap from Tuya. And
again, good cameras that don’t pull this bullshit are cheap! I did this just
because I wanted to see if I could.
