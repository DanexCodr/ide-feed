This is an evolutionary architecture guide for .NET software development, illustrating how applications can organically scale from simple beginnings to complex distributed systems. Championing a pragmatic approach, the guide advises developers to start with a minimal, manageable setup rather than over engineering prematurely with trendy tech stacks. This philosophy is demonstrated by building a fitness studio MVP using a single project divided into isolated bounded context modules and vertical feature slices. During that building, we discover the core principles of Evolutionary Architecture that center on allowing software structure to adapt and grow as business domain understanding and system needs evolve. These are: **Evolving with understanding (overcoming "The Project Paradox")**  
At the start of a project, developers understand the business domain the least. Evolutionary architecture defers major structural decisions until real domain knowledge and usage metrics exist, preventing early guesswork. **Avoiding over engineering and oversimplification**  
Systems should avoid premature complexity (such as adopting microservices, distributed streaming, or heavy orchestration "just in case"). Equally, systems must establish clear module boundaries early so monolithic growth does not degenerate into an unmaintainable "big ball of mud". **Context driven pattern selection**  
Rather than applying a single architectural pattern across the entire system, each module is assigned the exact level of complexity it requires. Simple areas can use direct data access or transaction scripts, while complex areas warrant Clean Architecture or Domain Models. **Clear domain boundaries and modular isolation**  
Each subdomain operates within its own bounded context and module boundary. Logic is organized into vertical slices by business process rather than technical layers, accompanied by separate database schemas to ensure strict isolation. **Extraction triggered by real "disintegrators"**  
Microservices are extracted from a modular monolith only when concrete operational factors exist, such as extreme load imbalances, vastly different deployment change frequencies, or distinct security independent deployment units. **Explicit Architecture Decision Logs (ADRs)**  
Furthermore, the framework relies on architecture decision records to document design choices.  
Architectural choices and trade offs are formally tracked alongside the codebase using immutable Architecture Decision Records (ADRs) These principles are examined throughout the chapters of the course, which a short overview follows: **Chapter 1: Initial architecture - Go for simplicity**  
The goal is to establish a lightweight, not overengineered foundation for an MVP. It uses a single production project (Fitnet) organized by module namespaces (Contracts, Passes, Offers, Reports) and vertical slices where all code for a specific business process live together. Data is isolated into separate database schemas per module and components communicate asynchronously via a simple in memory event bus. **Chapter 2: Modules separation - focus on maintainability**  
Here the goal is to resolve team merge conflicts and codebase complexity as the modular monolith grows. To do that it splits the monolith into purpose built projects per module and applies tailored architectural patterns according to each module's complexity. **Chapter 3: Microservice extraction - focus on growth**  
Scale out high traffic modules using concrete real world "disintegrators" by extracting the heavily used Contracts module into an independent microservice while retaining the remaining modules inside the modular monolith. On the way, it also replaces the in memory bus with RabbitMQ and MassTransit for distributed messaging, and publishes shared components/integration events as reusable NuGet packages. **Chapter 4: Applying tactical domain driven design - focus on complexity**  
Here we manage deep business domain logic within the extracted microservice, by refactoring the Contracts microservice to use rich DDD building blocks, including Aggregates, Entities, Value Objects and Domain Events. This enforces persistence ignorance, and isolating business rules from data storage and infrastructure concerns. The narrative of the chapters' succession is that as a system's requirements grow, the architecture naturally transitions through subsequent phases, separating modules and extracting microservices only when real world complexity demands it; these architectural design choices are fully justified. For instance: In Chapter 2, the team applied Clean Architecture specifically to the Contracts module (documented in ADR 0012) because of:

  * Handling high business complexity: Domain analysis revealed that Contracts was the core subdomain of the system with deep business rules that were projected to grow exponentially over time.
  * Strict separation of concerns: Clean Architecture organizes the module into four distinct layersCore (domain model and business rules), Application (use cases), Infrastructure (persistence and technical integrations) and API (HTTP endpoints).
  * High testability: Decoupling the domain logic from technical infrastructure (like databases or external frameworks) allows each layer to be tested independently.
  * Encapsulation and reduced cognitive load: Using distinct project layers provides fine grained control over visibility (what is public vs. internal), hiding internal implementation details and reducing cognitive load as business rules get more complex.

Then in Chapter 3, the architecture transitions from an in-memory event bus to RabbitMQ and MassTransit. The resons for this are: 

  * Microservice extraction: Due to extreme load, frequent changes and stricter security requirements, the Contracts module was extracted into an independent microservice.
  * Crossing process boundaries: The in memory event bus used in Chapters 1 and 2 only worked within a single deployment unit. Once Contracts became a separate service, messaging had to travel asynchronously over the network between distinct deployment units.
  * Message persistence and reliability: In memory messaging loses messages during application restarts or failures. RabbitMQ provides durable message persistence, ensuring events can be queued and processed reliably without data loss.
  * Fault tolerance and redundancy: Combined with MassTransit as a C# bus framework, RabbitMQ enables clustering, message retries and multi instance replicas to protect the growing system against random network or service failures
