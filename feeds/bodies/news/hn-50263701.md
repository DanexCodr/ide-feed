## Background

GoAhead is an embedded web server used for device management: routers, switches, printers, gateways, and industrial controls and is deployed in hundreds of millions of devices.

Each finding below affects a specific subset of those deployments, depending on the build and configuration.

GoAhead supports two TLS backends: OpenSSL, the default, and MbedTLS. The OpenSSL backend also works with compatible libraries such as LibreSSL.

GoAhead takes a compile-time approach regarding certain configurations:

- `ME_GOAHEAD_SSL_VERIFY_PEER=1` requires a client certificate.

- `ME_GOAHEAD_SSL_AUTHORITY` points at a PEM bundle of trusted CAs.

- `ME_GOAHEAD_SSL_VERIFY_ISSUER=1` requires the certificate chain to establish issuer trust against that bundle.

- `ME_GOAHEAD_SSL_REVOKE` points at a PEM-encoded Certificate Revocation List.

- The OpenSSL backend sets a chain-depth limit of 10 (`VERIFY_DEPTH`).

## Mbed TLS builds

GoAhead's mbed TLS backend configures the RFC 3526 2048-bit DH group through `mbedtls_ssl_conf_dh_param_bin()`. The modulus length passed to that function is taken from the generator buffer:

The size arguments tell mbed TLS how many bytes to read from each buffer. The call uses `sizeof(dhm_g)` for both, even though `dhm_g` is only one byte long. The length for `dhm_p` should be `sizeof(dhm_p)`, or 256 bytes.

As a result, mbed TLS reads only the first byte of `dhm_p`: `0xFF` (255). The remaining 255 bytes are discarded. It accepts this value and sends it to the client during the TLS 1.2 DHE_RSA handshake:

In ServerKeyExchange, `00 01 ff` identifies a one-byte DH parameter with the value 255. It should contain the full 256-byte value.

The broken parameters leave just eight possible shared-secret values : `01`, `02`, `04`, `08`, `10`, `20`, `40`and `80` in hex. An observer can try each candidate and identify the correct one by checking whether it decrypts the captured traffic successfully.

In the attached PoC, I managed to reproduce the shared secret after five attempts. It matched the client's secret, confirming that the same TLS session keys could be derived to decrypt the HTTP exchange.

A passive observer can decrypt captured sessions using the recorded handshake and encrypted application records completely out of band.

Exploitation requires a client that accepts the broken DH parameters. The tested OpenSSL client rejected them with `DH_check_params_ex: modulus too small`. Permissive clients, including custom or embedded implementations without a minimum-size check, can complete a decryptable session. ECDHE sessions and TLS 1.3 are unaffected by this configured finite-field group.

**Affected: **GoAhead 4.0.2 through 6.1.0 using the mbed TLS backend with TLS 1.2 DHE_RSA suites, where the client accepts the parameters. The typo entered in 2018 during migration to the binary-parameter API and survived the April 2024 TLS refactor. Mbed TLS 4.x removed the `TLS_DHE_*` suites, so this DHE path isn't impacted.

If you see any of these suites in the JA4S logs of your environment, you might be impacted (eg. `t120100_009f_1ca028f07214`)

## LibreSSL builds

Essentially, an attacker can present a certificate chain longer than GoAhead’s limit and still complete the mTLS handshake on an affected build. LibreSSL reports an issuer error instead of a depth error. GoAhead accepts that issuer error when issuer checking is disabled.

Error 20, `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`, is tolerated when issuer checking is disabled. Error 22, `CERT_CHAIN_TOO_LONG`, is rejected.

## Conclusion

All three findings affect GoAhead's integration with its TLS libraries. CRL enforcement depends on a verification flag, DH parameters depend on the supplied buffer lengths, and chain-depth enforcement depends on how verification errors are handled. None of these defects prevents the affected handshake from completing.

The backend and build configuration determine which defects apply. LibreSSL builds can inherit both the CRL defect in the OpenSSL-compatible backend and the legacy verifier's depth issue. The mbed TLS backend uses a separate verification path but is affected by the DH truncation when a client accepts the parameters.
