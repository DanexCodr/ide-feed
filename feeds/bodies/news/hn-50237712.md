Anyway. Enough about me. Let me share how I actually improved the performance.

It goes without saying that caching is essential. Get caching right and performance improves dramatically. And Next.js makes caching really convenient.
There’s [ISR](https://nextjs.org/docs/app/guides/incremental-static-regeneration-cache-components), and it also [extends `fetch` with a `next` option for caching](https://nextjs.org/docs/app/api-reference/functions/fetch#optionsnextrevalidate). Handy. Using these well alone gets you a long way on performance.

Unfortunately, though, our site can be reached from anywhere in the world. Why is that unfortunate? Within the same region, caching makes things fast, but visitors from other regions still end up eating the network latency.

Yes. That’s why we use a CDN. And if you deploy a Next.js app to Vercel, you get a CDN out of the box. I don’t dislike Vercel; it’s incredibly convenient. But the Pro plan is pricey right from the start, there’s the serverless cold start problem, and the dependency on the Vercel ecosystem isn’t something you can ignore either.

So why not use a different CDN service? Cloudflare, for example. I honestly think Cloudflare is a genuinely nice company. You can run large-scale infrastructure and most apps on it for free. But then I figured I didn’t really need Next.js’s caching anymore. Having to invalidate two caches every time I publish a post makes things a pain to manage.

In short, for a static website, I figured a CDN alone is enough. And that’s reason number one why I didn’t need Next.js.

Images these days run over 10MB. Serve those on the web as-is and your performance will go completely off the rails.

Optimizing images is quite a hassle. You have to resize per device, compress, and then handle the CDN on top of that. On a previous project, I had a serverless function (AWS Lambda) compress and resize images whenever one landed in storage (S3), and I put CloudFront in front as the CDN. It was a pretty reasonable setup for tailoring things exactly the way I wanted. But it’s also a setup that needs a fair amount of upkeep.

So this time I went with Cloudflare’s [Image Transformations](https://www.cloudflare.com/products/images/). Even on the free tier you get 5,000 images, so I use it without a second thought.

Pretty high scores. **But this isn’t enough. We want 100.** A clean, no-asterisks 100. So I dug into what the problem was.

![Lighthouse legacy JavaScript audit](https://korindiehacker.bloffy.blog/en/onerror=redirect/korindiehacker/articles/469/1791882757334-yydf5i)

It said a substantial amount of legacy JavaScript was found, and it wasn’t code I wrote. It came from the framework runtime that Next.js ships in its bundle.

But this page is a static page with zero interaction. Every page is pre-rendered with ISR, and I thought I’d followed the Next.js guidelines well. So as an experiment, I ripped out every client component the app had, left only server components, and measured again. The score didn’t budge.

**At first I suspected [hydration](https://nextjs.org/docs/messages/react-hydration-error), but once I dug in, the problem wasn’t hydration alone. The cause was the client runtime that Next.js always ships, even for static pages.** Even with only server components, the runtime chunks, hydration, and the RSC payload for the router all stay. That’s because `next/link` and `next/image` are themselves client components (`'use client'`), so having just those two is enough to pull in the runtime and trigger hydration.

So what if I strip out `next/link` and `next/image` too? The App Router’s own runtime, the router and error boundaries, still remains. There’s no official way to get it down to zero; the only option was a hack: stripping the scripts out of the rendered HTML. That’s when it hit me: “If I’m going to do that, why am I even using Next.js?”

![Coverage for qa-a.bloffy.co](https://korindiehacker.bloffy.blog/en/onerror=redirect/korindiehacker/articles/469/1791882784075-l7uuy)

You can see that the bulk of the JavaScript is code that isn’t needed. Unused code alone comes to 230,460 bytes. That’s not good.
Most static websites don’t need JavaScript at all. Unused JavaScript is needed even less.

This is where I really agonized. Is dropping Next.js for the sake of 100 points the right call? I’d spent a lot of time building the public-facing web app.

In the end, for the quality of the blog (even if it’s just 5 points), I decided to rip Next.js out entirely. My judgment was that I wouldn’t need Next.js’s excess features in the long run either. I considered going fully vanilla, but I didn’t want to give up the productivity and infrastructure benefits of a framework. I needed to find the right one.

I chose [Hono](https://hono.dev/). I liked its technical philosophy. “Fast and simple” was exactly the solution I needed most, and JSX support was a bonus. The migration cost didn’t look too big, either.

![PageSpeed Insights screenshot of Bloffy on qa-b](https://korindiehacker.bloffy.blog/en/onerror=redirect/korindiehacker/articles/469/1791882802426-g8nmm)

Tada. And just like that, 100 across the board. Go ahead and run the very page you’re reading right now through [pagespeed.web.dev](https://pagespeed.web.dev/).

![Coverage for qa-b.bloffy.co](https://korindiehacker.bloffy.blog/en/onerror=redirect/korindiehacker/articles/469/1791882889483-fhhrlh)

There’s no JavaScript, and unused code dropped sharply to 407 bytes. As a bonus, build time went down by about 40% too.

The long task that runs before anything is rendered on screen took 309.3ms on Next.js, and when I built the same page with Hono, it took 68.01ms. That’s roughly a 78% improvement.

Is a JS payload, hydration included, really doing a static site any good? I don’t think so. It leaves behind unnecessary JavaScript, so in most cases I think it’s simply not needed.

> That said, for an interaction-heavy app, I think Next.js can be a great framework. In fact, the management app for this very blog is built with Next.js!
