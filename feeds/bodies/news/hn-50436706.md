# What is Xata

It’s undeniable that this year software development has changed forever, with agents and software factories now doing the grunt work. However, the increase in coding output has uncovered new bottlenecks. For many companies the database workflows are now the bottleneck: every pull request and every agent run needs a safe, isolated database with production-like data.

Traditionally, creating a copy of a production database is a slow and expensive process, especially when dealing with terabytes of data. Creating a database for every pull request or agent run simply doesn't scale with traditional cloning. With copy-on-write branching, however, there's no need to copy the data, making it possible to create a new branch with production data in seconds.

This is exactly what we’ve built at Xata. Even if a database has multiple terabytes of data, creating a branch takes only around 3 seconds. This means the schema and the data appear as if they were instantly copied to the child branch. At the same time, the child branch is fully independent: it has its own compute, running on a different physical node, and nothing that happens on the child branch impacts the parent database.

The key capabilities are:

- Instant database provisioning: Create a new, fully functional Postgres database instantly.
- Instant copy-on-write branching: Create database branches in seconds, without duplicating the underlying data. You only pay for the diff: create 50 branches of a 1TB database and you’re billed for something much closer to 1TB than 50TB.
- Scale-to-zero compute: Automatically suspend idle databases and wake them on the next connection, in about one second, minimizing costs.
- Anonymized production data: Remove sensitive information before data leaves production, so developers and agents can safely work with database branches.

Together, these capabilities make it [remarkably cheap](https://xata.io/blog/a-thousand-postgres-branches-for-1) to run a branch per PR, per agent run, or even per SQL session. AI-native customers like [Sapien](https://sapien.ai/), [Enginy](https://www.enginy.ai/), [David AI](https://www.withdavid.ai/), [Runner AI](https://www.runnerai.com/), and [LoopAI](https://www.loopai.com/) each create thousands of database branches every week.

You might also know Xata from our [open-source projects](https://xata.io/open-source) in the Postgres ecosystem, including **pgstream**, for logical replication with anonymization and DDL support, and **pgroll**, for zero-downtime, reversible schema changes.

# What Xata enables

## A database branch for every pull request and agent run

The GitHub integration enables automatically creating an isolated database branch for every pull request. These branches can be integrated into CI/CD pipelines, allowing code changes to be safely tested before merging into production. Since they are only needed for testing, branches are often scaling to zero after only a few minutes, minimizing costs.

The same approach applies to coding agents, where every agent run can have its own isolated database to develop and test changes without affecting production.

For details on the branch-per-PR use case and the cost savings it provides, see [this blog post](https://xata.io/blog/a-thousand-postgres-branches-for-1).

## Powering AI platforms

AI platforms that embed Postgres are seeing an explosion in demand: first thousands, then hundreds of thousands, and eventually millions of databases per week. There are two main use cases: **instant database provisioning** for every new application, and **a database branch for every deployment preview**, allowing code changes to be tested safely against production data.

Because unused databases scale to zero, platforms can run very large fleets of small, mostly idle databases at a fraction of the cost, while keeping full compatibility, since it's simply vanilla Postgres.

# How it works

Two key technologies enable fast branching and short wake-up times: our Xatastor storage engine and warm pools for compute instances.

**Xatastor** is our storage engine, which provides separation of storage and compute, high multi-tenancy, copy-on-write branching, compression, thin provisioning, and more. It exposes ZFS zvols over the network using the NVMe/TCP protocol. Because it works at the block-device level, we can run unmodified vanilla PostgreSQL. For a deep-dive into the Xatastor architecture, see this dedicated [blog post](https://xata.io/blog/xatastor-zfs-nvme-of-for-millions-of-postgres-databases).

We use **warm pools of compute instances** to obtain super fast provisioning, wake-up after scale-to-zero, and branching times. This removes the actual node and pod provisioning from the hot path of making a new database or branch available. You can find more information about how this works in this [blog post](https://xata.io/blog/a-thousand-postgres-branches-for-1).
