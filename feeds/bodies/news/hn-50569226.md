This fixes "Buffer overflow in EVP_EncodeBlock()" ([CVE-2026-121481](https://github.com/advisories/GHSA-83xj-7xh4-4p7x)) by returning `-1` for invalid inputs to `EVP_EncodeBlock()`: `NULL` input or output buffers, negative lengths, and lengths for which the encoded size does not fit in an `int`. The OpenSSL SRT has asked for it to be fixed publicly; the advisory is still pending.

Returning `-1` for invalid inputs is the most straightforward fix, and matches what happens in [wolfSSL's compatibility layer for OpenSSL's EVP_EncodeBlock()](https://github.com/wolfSSL/wolfssl/blob/779d388f837aec1cf59f609621f79d3605f2bb94/wolfcrypt/src/evp.c#L14051-L14060).

I'm suggesting a similar guard for `EVP_DecodeBlock()`. No length limit is needed here because the decoded length always fits in an `int`, but it is a good idea to reject `NULL` buffers and negative lengths.

Moreover, I propose to fix the incorrect length check in the `base64encode()` function of `http_client.c`, which rejected only `len > INT_MAX`.

Exploiting this vulnerability from the command line is possible by passing a large `-proxy_pass` to `openssl s_client`. I confirmed that [GOST](https://gost.run/en/) accepts these large passwords out of the box. However, the password has to be supplied through an environment variable (`env:VAR`), otherwise the command line will be too long.

Note: the pattern of [CVE-2026-121481](https://github.com/advisories/GHSA-83xj-7xh4-4p7x) is similar to that of [CVE-2021-23840](https://nvd.nist.gov/vuln/detail/cve-2021-23840).
