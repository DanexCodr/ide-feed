Apache Pulsar 5.0 has been released, with the addition of scalable topics, which grow and shrink with demand while preserving per-key ordering. The new version also has a new Java client API and Oxia as the recommended metadata store for new clusters.  Apache Pulsar is an all-in-one messaging and streaming platform that combines features of traditional message queues and streaming systems.. It has a layered architecture, is multi-tenant, and provides a high-performance solution for server-to-server messaging. It was originally developed by Yahoo.  Pulsar's architecture separates the compute from storage. It supports microservices, real-time data pipelines, geo-replication, tiered storage, and built-in stream processing. The headline improvement of this release is scalable topics: topics that size themselves. The concept of topics is that of named stream that applications publish to and consume from. Until now, Pulsar has required developers to specify the number of partitions needed for a topic, and this figure couldn't be decreased. Increasing it meant creating hot partitions and costly migrations; choose too many and you pay for resources a quiet topic never needed. A scalable topic is a single logical stream whose capacity follows its actual load, in both directions. Segments can be defined as key-range segments that contain a single topic in a contiguous range. Topics can also be split and merged at runtime. The broker automatically splits hot segments and merges adjacent cold ones with no downtime. Applications don't need to know about segments, they see one single stream. This version also adds a new v5 Java client API. This is a complete redesign of Pulsar's client API, which the developers say grew one feature at a time over the last decade, accumulating options, overloads, and subtle inconsistencies. Areas where the new API is improved start with consumption. The v4 client offers a single Consumer shaped by one of four subscription types (Exclusive, Failover, Shared, and Key_Shared), plus a separate Reader, with behavior that shifts as options are combined. The v5 API replaces them with three purpose-built consumers, each exposing only the operations that make sense for it, so stream consumers are used for ordered consumption with cumulative acknowledgment, including key-shared processing across consumers. Queue consumers handle parallel work-queue processing with individual and negative acknowledgments and dead-letter handling; and Checkpoint consumers deal with stream-processing engines such as Flink and Spark that track their own position, with no subscription or acknowledgment. Because of the addition of scalable topics, clients need to track the segment layout as it changes, route each key to the segment that owns it, and follow the controller's consumer assignments. To make every client behave the same way, Pulsar 5.0 also ships the Scalable Topics Client Specification 1.0, a language-neutral contract for scalable topics clients. At the moment, only the Java v5 client supports Scalable Topics, but the developers say work is ongoing to bring that support to the other Pulsar client SDKs. This release also has changes aimed at performance and reliability improvements, with a performance testing framework that suggests ways to fine tune the system. Improvements include fewer thread handoffs to avoid context switching and internal thread coordination; and reduced contention due to streamlined synchronization and locking mechanisms lowering CPU overheads.  Pulsar 5 is available now.
