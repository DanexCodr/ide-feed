Given an SFT dataset, we can predict exactly the LoRA size required to fit it.

> **TLDR:**
>
> - We develop a predictive theory of the capacity of a LoRA adapter as a function of its rank.
> - Unlike full-parameter fine-tuning, LoRA learns a decreasing amount per-parameter.
> - Given an SFT dataset, we can predict the LoRA size required to fit it.

At Engram, we train lots of models. We train models for individual users and update them when information changes. A major focus of our research is how to customize and adapt models efficiently at scale.

This post focuses on LoRA<sup>[1](https://engram.com/blog/lora-size#sidenote-1)</sup>. LoRA has become the predominant approach for customizing models in industry. While there exists a large body of knowledge on how to set the hyperparameters and train LoRA effectively<sup>[2](https://engram.com/blog/lora-size#sidenote-2)[, 3](https://engram.com/blog/lora-size#sidenote-3)</sup>, it’s still unclear how to set LoRA’s rank. Although it’s agreed-upon that LoRA underperforms full-finetuning on larger datasets, it’s not clear when this is the case. How big does a dataset have to be to require a larger LoRA?

In practice, smaller LoRAs enjoy a number of systems advantages, being lighter to load<sup>[4](https://engram.com/blog/lora-size#sidenote-4)[, 5](https://engram.com/blog/lora-size#sidenote-5)</sup>, faster to generate text from<sup>[6](https://engram.com/blog/lora-size#sidenote-6)</sup>, and easier to store on disk. For larger models, rank-1 can store quite a lot; some datasets, like RL data, can be represented in a small number of bits and often fit within a rank-one LoRA adapter (or smaller!<sup>[7](https://engram.com/blog/lora-size#sidenote-7)[, 8](https://engram.com/blog/lora-size#sidenote-8)[, 9](https://engram.com/blog/lora-size#sidenote-9)</sup>).

In this post, we develop a predictive theory and practical approach for sizing LoRA adapters to a new dataset. The idea is simple: the size of the LoRA required depends on how many bits it takes to encode the dataset under the base model. We use this idea to derive an exact formula for how many bits a single LoRA adapter can learn as a function of its rank.

We then extend our idea to measure the capacity of LoRA on full transformers. Since theory can’t predict the nonlinear behavior of deep transformers, we turn to an empirical solution: we generate synthetic datasets of exactly NNN bits under the base model and train on them to measure LoRA’s capacity. Our capacity predictions hold up on real datasets: across a variety of settings, we can accurately determine the necessary rank of the adapter.

**Generating *exactly* N bits using an LLM**

To measure the capacity of LLMs being trained with adapters, we need to generate data with a controllable number of bits. Prior work in this space creates data of fixed size with random generative processes, like randomly generated tables of facts<sup>[13](https://engram.com/blog/lora-size#sidenote-13)</sup> or random strings of tokens.

To generate truly random data from an LLM, we leverage a tool called arithmetic coding. Arithmetic coding gives us the ability to transform probability distributions into codes; it represents the entire code using a single floating point number in [0,1)[0, 1)[0,1) that we can turn into a sequence using pθp_\thetapθ​.

We take this one step further. A pretrained open-source model like Qwen or Inkling already provides likelihoods for text, so we can run arithmetic coding in reverse: start from NNN random bits and decode them into text. The result is a sample from pθp_\thetapθ​ whose code length under the model is NNN bits. One can think of this as an implementation of Neural Linguistic Steganography<sup>[14](https://engram.com/blog/lora-size#sidenote-14)</sup> using randomly selected codes.

In this example, `queen` is worth eleven bits (surprising!), while `little` carries just two bits. Later in this post we will generate many strings like this to build a dataset of exactly known size, then train an adapter on it to measure how many bits it can learn.

### Sizing LoRA, in theory

Prior work has estimated that the capacity of full transformer training scales roughly linearly with parameter count<sup>[15](https://engram.com/blog/lora-size#sidenote-15)[, 16](https://engram.com/blog/lora-size#sidenote-16)[, 17](https://engram.com/blog/lora-size#sidenote-17)</sup>. We don’t intuitively expect this to be true with LoRA, since some dimensions influence the model outputs more than others. Instead, we expect diminishing returns to capacity as rank increases. This is exactly what we see in practice, and it turns out we can predict the capacity curve quite cleanly using a simple statistical model.

Suppose we sample data from a model and then adapt one of its weight matrices to memorize that data. How much can we expect to increase the log-likelihood (and hence decrease the code length) with a rank-rrr adapter? To second-order, log⁡pθ(x)\log p_\theta(x)logpθ​(x) looks like an inverted bowl in parameter space. How high we can climb on that bowl can be determined from the gradient and Hessian at the point θ\thetaθ, and these are both random functions of the training data xxx. Since the data is sampled from pθp_\thetapθ​, the statistics of the gradient and Hessian are determined by the Fisher information matrix, which greatly simplifies the calculations.

### Sizing LoRA, in practice

Theory predicts around 0.5-1.4 bpp when perturbing individual weight matrices. What about full transformers? When we adapt several matrices *jointly*, the capacity is more than the sum of its parts. We see super-additive scaling of capacity thanks to complementary interactions from adapting multiple weights at once<sup>[19](https://engram.com/blog/lora-size#sidenote-19)</sup>.

While the theory above cannot explain these super-additive effects yet, we do have a way to generate a dataset of a fixed size (measured above) and a way to measure how much a model learns from data (by checking its loss).

## Sizing LoRA capacity with real datasets

Remember that our goal is to estimate the rank of LoRA required to fit some arbitrary SFT dataset. To do this, we need a method for measuring the size of datasets. In the previous section, we used log-likelihood under θ\thetaθ as a way to generate synthetic data of a precise size. Following the same logic, we can measure the log-likelihood of real data to compute its size under θ\thetaθ.

### Measuring the size of full datasets

We first extend the model’s context window to 2M tokens via YaRN<sup>[22](https://engram.com/blog/lora-size#sidenote-22)</sup>. If the data still doesn’t fit into context, we estimate its size in bits under the model by cutting it into windows of 2M tokens and summing the log likelihood:

### Testing on real workspaces

We now test our ability to properly allocate adapters and train. We test on datasets of varying sizes scattered across the public internet as well as our and our partners’ workspaces.

For each new dataset, we first measure its size in bits under the model and read the predicted rank rrr off the synthetic capacity curve. We then train LoRAs on the real dataset itself at ranks from r/2r/2r/2 to 2r2r2r, and report the measured rank as the smallest rank that stores 95% of the dataset.

Even though our capacity estimates assume the training data is drawn from the base model, our predictions are extremely accurate on real datasets: the orange dots, the smallest LoRAs required to fit each dataset in practice, fall almost on the blue line, our estimate of a given LoRA rank's capacity.

## Conclusion

This post described our work to automatically provision adapters of a fixed size by using information theory to estimate adapter capacity and relate it to the size of a given dataset. This gives a way to mint PEFT modules on-the-fly of the minimum size required for a given task.

In practice, we don’t always use LoRA. We’re exploring other options for parameter-efficient learning such as trainable prefixes<sup>[23](https://engram.com/blog/lora-size#sidenote-23)</sup>, sparse memory layers<sup>[24](https://engram.com/blog/lora-size#sidenote-24)</sup>, steering vectors<sup>[25](https://engram.com/blog/lora-size#sidenote-25)</sup>, GDN state, and trainable experts<sup>[26](https://engram.com/blog/lora-size#sidenote-26)</sup>. We find the landscape of PeFT methods contains a number of tradeoffs, and different modules work better for different tasks. We’re also working on other parts of this stack, such as more accurately estimating loss without training and understanding capacity in the finite-compute regime.

On a broader scale, examining how model capacity interacts with data size provides us a clean playground to investigate fundamental questions around how models learn.

### A: Theory

Intuitively, the capacity of the adapter is the number of bits it can store about the data it is trained on. We formalize this concept as the decrease in code length of training data, on average over the training distribution. When the training distribution differs from the base model, the decrease in code length comes from a combination of learning the *signal* — the change in distribution — and *noise* — the particulars of the individual training samples. We can simplify our study of capacity by sampling from the base model, eliminating the signal so that any reduction in code length comes from memorizing the noise in the training samples. While this is unrealistic, it gives conservative worst-case estimates of capacity per parameter, and as we will empirically demonstrate, the theory is predictive in more realistic settings as well.
