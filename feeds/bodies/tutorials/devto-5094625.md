Connecting one agent to one MCP server is easy. You paste a URL, approve a prompt, and the agent starts calling tools.

Then the second agent shows up. Then the fifth MCP server. Then someone asks which credentials the agent is using against the CRM, and nobody has a clean answer.

That is the point where an MCP gateway starts to matter.

> **Which agent can call which tool, with whose credentials, and who can prove it afterward?**

An MCP gateway sits between agents and MCP servers. It gives agents one endpoint to connect to, decides which tools each caller can see and run, handles upstream authentication, and logs what happened.

Without one, every client holds its own server list, its own tokens, and its own idea of what "allowed" means. That works on a laptop. It gets messy in production.

![Diagram of agents connecting through one MCP gateway to multiple MCP servers](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/ukr4blaukasvppt6ulwp.png)

## First, what does an MCP gateway actually do?

Most MCP gateways cover a similar core set of jobs:

1. **Aggregation.** Many MCP servers show up behind one endpoint, so clients configure one URL instead of ten.
2. **Authentication.** The gateway handles the sign-in on the agent side and the credentials used on the server side, including OAuth flows.
3. **Tool filtering.** Not every agent needs every tool. The gateway decides which tools are visible and callable per user, team, or key.
4. **Logging and tracing.** Every tool call leaves a record you can search later.
5. **Cost and context control.** Large tool catalogs burn tokens just by being described to the model. Some gateways help with that too.

Some products are MCP-only. Others come from the LLM gateway or API management world and added MCP on top. Neither is better by default. It depends on what you already run.

## The gateway is not the MCP server

This gets mixed up a lot.

The MCP server exposes tools. The agent decides when to call them. The gateway only decides whether the call is allowed to reach the server, and what comes back.

Think of it as a front desk with a visitor log:

- Who is this caller?
- Which servers and tools can it see?
- Is it allowed to call this one, with these arguments?
- Which credential does the upstream server get?
- What did the tool return, and should the model see all of it?

If you have ever put an API gateway in front of services, this will feel familiar. The difference is that the caller is an agent that decides on its own how many calls to make.

## Why server-level access is not enough

Letting an agent connect to the GitHub MCP server is a coarse decision. The real question is which tools on that server it can use.

```text
Can the support agent read tickets? Yes.
Can it close tickets? Maybe.
Can it delete a repository? No.
Can it call the production version of a tool? Only with approval.
```

Those are tool-level questions. A gateway that only allows or blocks whole servers will not answer them.

The risky part also does not end at the request. A tool can be allowed to run and still return a token, a customer record, or a poisoned instruction that the model then acts on. Good control covers both directions.

## What a production MCP gateway should actually do

There are six things worth evaluating. Everything else is detail until these are clear.

| Control | The question to ask | Why it matters |
| --- | --- | --- |
| Tool-level policy | Can it allow, deny, and scope individual tools, not just servers? | Tools read and change real systems. |
| Identity | Can it identify the agent and the person or service behind it? | One shared token is not governance. |
| Upstream auth | Does it manage OAuth and credentials per user and per server? | Agents should not hold long-lived secrets. |
| Observability | Can you trace a tool call back to the caller and forward to its result? | Incidents rarely stay inside one request. |
| Context cost | Does it reduce the token cost of large tool catalogs? | Tool definitions add up fast. |
| Deployment | Can it run where your data and credentials are allowed to be? | Security rules often decide this before features do. |

The two questions that separate a real evaluation from a feature checklist are:

> Can it block a risky tool call before execution?

> Can it revoke one agent's access immediately, without redeploying anything?

If the answer is "we can see it in the dashboard later," that is observability, not control.

## Eight MCP gateways worth putting on a shortlist

This is not a universal ranking. "Best" depends on where you run, what you already operate, and whether you want a managed service or something your team owns.

Product capabilities change quickly in this category. Treat the list as a shortlist for a proof of concept, then verify current documentation, licensing, and tier limits before a long-term decision.

### 1. Bifrost

![Bifrost](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/fbhhkygkku15c2618jia.png)

**Best fit:** Teams that want one self-hosted gateway for MCP tools, model traffic, and agent-to-agent calls, especially where VPC, on-prem, or air-gapped deployment matters.

[Bifrost](https://www.getmaxim.ai/) acts as both an MCP client, connecting to your tool servers, and an MCP server, exposing one governed endpoint to clients like Claude Desktop or Claude Code. Your agents connect once, and new servers behind the gateway show up without touching every client.

Access control runs through [virtual keys](https://docs.getbifrost.ai/features/governance/virtual-keys). Each key can carry an allow-list of MCP clients and individual tools, and the same key also holds the model scope, budget, and rate limit. Tool filtering is [layered](https://docs.getbifrost.ai/mcp/filtering): request headers can narrow what a caller sees but never widen it, and the published model supports blocking tools by default until a key is granted access. [Virtual MCP servers](https://docs.getbifrost.ai/mcp/virtual-mcps) bundle tools from several servers into one curated endpoint for a team.

The feature that is easy to underestimate is Code Mode. Instead of loading every tool definition into context, Bifrost presents connected servers as compact stubs the model can read on demand. In a [benchmark](https://github.com/maximhq/bifrost-benchmarking/blob/main/mcp-code-mode-benchmark/benchmark_report.md) that grew from 96 tools across 6 servers to 508 tools across 16 servers, Code Mode cut input tokens by 58.2% to 92.8% and estimated cost by up to 92.2%, with pass rates holding at 100%. The savings grow as the tool count does. The [Code Mode docs](https://docs.getbifrost.ai/mcp/code-mode) cover the setup.

It also covers per-user OAuth sign-in, approval before a tool call runs, MCP logs with tool cost and call volume, [deployments inside a customer VPC](https://docs.getbifrost.ai/enterprise/invpc-deployments), and an [Agent Gateway](https://docs.getbifrost.ai/features/agent-gateway/overview) for A2A traffic. Audit logs are listed under the enterprise tier.

**Ask during evaluation:** Can one virtual key govern the model request, the MCP tool call, and the budget together?

### 2. Kong AI Gateway

![Kong AI Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/qjsop7686up0tve0yby1.png)

**Best fit:** Organizations already running Kong Gateway or Kong Konnect for API management.

[Kong AI Gateway](https://docs.konghq.com/gateway/latest/ai-gateway/) is compelling when the infrastructure team already trusts Kong with normal API traffic. Instead of adding a separate control plane for agents, the team extends the existing one to cover MCP.

Kong publishes central authentication, authorization, rate limiting, audit trails, and MCP server generation on top of managed APIs. That last one matters if your tools are really existing REST APIs: you can expose them as MCP tools without writing a server for each.

The tradeoff is obvious too. If you do not already use Kong, adopting a broad API management platform only for MCP traffic may be more platform than you need.

**Ask during evaluation:** Are tool-level controls as mature as the model-side controls for the exact MCP flows you run?

### 3. LiteLLM

![LiteLLM](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/ggsunzme2hlx48ynyb64.png)

**Best fit:** Teams that want an open source, self-hosted Python proxy that covers MCP alongside model routing.

[LiteLLM](https://docs.litellm.ai/) started as a way to call many model providers through one interface. Its proxy now includes an [MCP gateway](https://docs.litellm.ai/docs/mcp), so MCP servers sit next to model traffic with access checked per virtual key and team. It is MIT licensed and runs in your own environment.

It is a Python service you operate yourself, so plan for the database, upgrades, and scaling. Some governance features, such as SSO and audit logs, are listed under its enterprise offering, so check what the open source tier covers for your requirements.

**Ask during evaluation:** Can your team own the proxy, its database, and its upgrade path, and which governance features does your tier include?

### 4. Amazon Bedrock AgentCore Gateway

![Amazon Bedrock AgentCore Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/joaalrmx1jfcbaxuze7n.png)

**Best fit:** AWS-native teams that want a fully managed gateway and are comfortable keeping the control plane inside AWS.

[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/) can turn APIs, Lambda functions, and existing services into MCP-compatible tools. It supports inbound identity checks, outbound credential injection, OAuth flows, and tool search, which helps when an agent faces a very large catalog.

This is the quickest route for a team already building on Bedrock and AWS identity. There is less gateway infrastructure to run and fewer components to assemble.

The limit is also clear. It is a managed AWS service. If you need on-prem deployment, a multi-cloud control plane, or an air-gapped environment, this is probably not the right baseline.

**Ask during evaluation:** Which credentials remain AWS-managed, and which identities can be passed through to downstream tools?

### 5. IBM ContextForge

![IBM ContextForge](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/qhg5seqwv6oq6otifhbq.png)

**Best fit:** Teams that need to federate a messy real-world collection of MCP servers, REST APIs, gRPC services, and agents.

[IBM ContextForge](https://github.com/IBM/mcp-context-forge) is more about discovery and federation than about being only an MCP proxy. It can put multiple internal services behind one endpoint and translate REST or gRPC services into tool-friendly forms.

That makes it interesting when the real problem is "how do I give agents a safe catalog of twenty years of internal APIs?"

Its published capabilities include user-scoped OAuth, retries, rate limits, OpenTelemetry, an admin UI, and air-gapped deployment support.

**Ask during evaluation:** Do you need per-agent hard budget enforcement, or is tool and service federation the primary problem?

### 6. Azure API Management

![Azure API Management](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/a7nazj2xy06m3996h1qg.png)

**Best fit:** Teams already running Azure API Management that want MCP traffic governed by the same policies as the rest of their APIs.

Microsoft's AI gateway is not a separate product. It is a set of capabilities on Azure API Management, so the policies, monitoring, and developer portal your API team already uses extend to MCP. APIM can expose a REST API or an existing server as an [MCP server](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview), with policies for rate limits, JWT validation, and IP filtering. Monitoring runs through Azure Monitor and Application Insights.

Check the details against your plan. The docs I reviewed list limits: MCP support covers tools but not resources or prompts, and MCP policies currently apply to all tools on a server, which makes per-tool rules harder. Some newer features arrive first through an early release channel on classic tiers.

**Ask during evaluation:** Do you need per-tool policy, or is server-level control enough for your use case?

### 7. Docker MCP Gateway

![Docker MCP Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/40lhx8q04i7uhvrtwbly.png)

**Best fit:** Developer teams that want MCP servers running in isolated containers, with a gateway that fits into a Docker workflow.

The [Docker MCP Gateway](https://github.com/docker/mcp-gateway) is open source and works as a proxy between clients and MCP servers. It runs each server in an isolated container with restricted privileges, network access, and resources, and starts a server on demand when a tool is requested.

Its security flags are practical. The gateway supports signature verification for images, call logging, and secret blocking, and it can expose only a subset of tools from each server. Profiles group servers per use case and can be shared through OCI registries. Distributed tracing through OpenTelemetry shows the path from the gateway down to the server operation.

The scope is narrower than a full enterprise gateway. Docker's docs note that the MCP Gateway as part of Docker AI Governance is an invite-only feature, so the centralized governance story goes through Docker sales. The open source gateway is strongest as a secure runtime for MCP servers, not as a central identity and budget layer.

**Ask during evaluation:** Is container isolation the main concern, or do you also need central per-user identity and policy?

### 8. Cloudflare MCP Server Portals

![Cloudflare MCP Server Portals](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/p65swnkjd8wu6pb0bkzf.png)

**Best fit:** Organizations already using Cloudflare One and Access that want MCP governed like any other corporate application.

[Cloudflare MCP Server Portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals) put multiple MCP servers behind a single portal URL. Users authenticate through Cloudflare Access with the corporate identity provider, and Cloudflare decides which servers they can see, whatever the upstream server's own authorization looks like. Admins can customize tools and policies per portal, and request logs from all servers land in one place.

It can also connect to MCP servers that exist only on a private network, and an optional Gateway path adds DLP inspection to the traffic. Cloudflare's announcement framed the feature as part of a Zero Trust model, so device posture and similar Access controls fit naturally.

The tradeoff: it makes the most sense if you are already in the Cloudflare ecosystem. Cloudflare launched it as an open beta, so check the current status and plan limits before you plan around it.

**Ask during evaluation:** How granular can tool-level policy get inside a portal, and which controls need a paid Cloudflare One plan?

## The tool boundary is the real test

Every vendor can show you a clean demo of an agent calling a tool.

The better test is a tool call that should be denied.

```text
Agent: "Delete the inactive customer records."
Tool request: DELETE /customers?status=inactive
Policy: this agent may read customer data, but may not delete it.
Expected result: tool execution never happens.
```

Now make it harder:

```text
Agent: "Issue a refund under $50."
Tool request: refund(customer_id, amount)
Policy: agent may refund up to $50 only for the current user's account.
Expected result: identity, amount, ownership, and tool argument rules all pass before execution.
```

Then test the return path:

```text
Tool result: contains an access token or another customer's data.
Expected result: the result is blocked or redacted before the model sees it.
```

That last one gets missed. A tool can be allowed to run and still return something the model should not receive.

You want controls before execution and controls after execution.

## An MCP gateway evaluation that will not waste three weeks

Do not start with a vendor demo. Start with three real agent journeys from your environment.

### Journey 1: the normal safe path

An agent reads an internal document through an MCP tool, summarizes it, and opens a draft ticket. This proves ordinary routing, identity, and logging work.

### Journey 2: the request that must stop

An agent tries a tool outside its scope. This proves the gateway prevents execution rather than just reporting it.

### Journey 3: the big tool catalog

Connect five or more MCP servers and measure how many tokens go to tool definitions before the agent does any work. This shows whether the gateway helps with context cost or just forwards everything.

For every journey, ask for four pieces of evidence:

1. The caller identity
2. The policy decision
3. The upstream request and result, with sensitive data redacted
4. The trace that connects the agent request, the tool call, and the final output

If a product cannot make that evidence easy to collect, incident response will be unpleasant later.

## The questions people forget to ask

### Can it use the end user's identity?

An agent acting as the user should not quietly become a service account with broader access. Check whether the gateway can exchange, forward, or scope identity per user and per tool.

### Can it kill access instantly?

If an MCP server is compromised or an agent starts behaving badly, can you disable one key or tool bundle immediately without redeploying every client?

### What about tool descriptions?

A malicious or poisoned tool description can steer an agent. Ask whether the gateway pins or reviews tool definitions, and what happens when a server changes them.

### Does it cover every transport?

MCP runs over several transports, including stdio, SSE, and streamable HTTP. Ask which paths get the same identity, policy, and audit coverage.

### Who runs the upstream servers?

A gateway that proxies third-party servers inherits their risk. Ask where servers run, how they are isolated, and how updates are verified.

## The honest conclusion

An MCP gateway is not a magic layer that makes agents safe.

It is the place where you can finally make the rules visible and enforceable.

The right gateway is usually not the one with the longest feature list. It is the one that fits where you already run, covers the transports you actually use, stops the tool call you are afraid of, and leaves enough evidence behind for someone else to understand the decision.

Start with your risky tool call. Everything else gets clearer after that.
