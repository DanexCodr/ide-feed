## The problem

Coding agents like Claude Code and Cursor are great, but they cost money, and not everyone wants (or can afford) a subscription. Meanwhile, free chatbots like ChatGPT and Claude.ai are sitting right there, perfectly capable of writing good code, as long as you can get your project's context in front of them and get the resulting changes back into your files without losing your mind 🤔

That gap, pasting context in and applying diffs back out, is tedious enough that most people just don't bother. They either pay for an agent or they give up and do it manually, file by file.

## Enter ReptClip

[ReptClip](https://github.com/effessdev/reptclip) is a free, open source VS Code extension that closes that gap 🙂 It lives right in VS Code's bottom panel, as its own tab next to your terminal, so there's no separate window or webpage to juggle. No API key, no subscription, no vendor lock-in. It works with literally any free chatbot you could find online.

Here's what the whole loop looks like in practice:

{% embed https://youtu.be/uWW3-1K-aGk %}

Here is the explanation. It's a 3-step process:

1. **Copy context to clipboard.** Pick the files you care about (by path or glob pattern), hit the "Context" button, and ReptClip copies your project structure, AI instructions, and the file contents as clean Markdown straight to your clipboard (each section can be easily toggled on/off).
2. **Paste into your chatbot.** Drop it into ChatGPT, Claude, Gemini, whatever you're using, along with your prompt.
3. **Apply the diffs.** The chatbot replies with its normal explanation, along with a single code block containing Search/Replace diffs. Copy that block, click "Apply Diffs" in the ReptClip panel, and your files are updated!!! 😎

If the chatbot needs to see more of your project mid-conversation, it can ask for it, and you feed that back in with one more click.

Some things that make it safe to actually trust with your codebase:

- **ReptClip only touches files that are tracked by git.** Anything your `.gitignore` files (at any depth) exclude is completely off-limits, for reading, searching, writing, creating, or deleting. `.git` folders are always off-limits too. Changing a `.gitignore` file always asks for confirmation first, since that can un-ignore something that was previously protected. If something ever goes wrong anyway, you can simply discard the changes with git.
- **Applying a diff is all or nothing.** If one block fails to match, nothing gets written. Fuzzy matching handles whitespace and line-ending differences, but still requires a unique match.
- **You get 10 levels of Undo/Redo** specifically for applied diffs, separate from your normal editor undo.
- **And MUCH more!** 🙂 [README](https://github.com/effessdev/reptclip)

The UI state is saved per project automatically, so you don't have to re-enter when you come back or be mixed up with other projects.

## What's new in v2.0

This is a major version bump. The headline feature is a complete rework of how ReptClip feeds extra context to your chatbot mid-conversation, and it also brings several useful new features for applying diffs 🎉

### "More Files" is gone. Say hello to "More Context."

In v1, if the chatbot wanted more files, it would ask for a list of files. That's it. That's all it could ask for.

In v2.0, the chatbot can generate a small command block containing three types of commands, and ReptClip generates the output (no subprocess) and copies it to your clipboard!

- `cat <path>` reads a full file.
- `grep <flags> <pattern> [paths...]` searches your project's contents, ripgrep-style, running in-process (no subprocess spawned).
- `read-lines <path> <start> [end]` pulls a specific, 1-indexed line range out of a file, handy for huge files where you only need a slice.

So instead of the chatbot blindly asking for whole files it might not even need, it can now search your codebase for the right TODO, grep for every usage of a function, or read just the relevant 20 lines of a 2,000-line file. It supports the flags `-i`, `-w`, `-F`, `-g`, `-m`, `-v`, and more. Everything still respects your `.gitignore` the same way the "Context" button does.

Click "More Context," and it works exactly the way "More Files" used to: read the clipboard, validate everything up front (so a bad path or invalid pattern fails the whole batch with a clear error instead of a half-built result), then build the output and send it back to your clipboard or output file.

### Line counts in the project structure

The "Project structure" section now lists each file with its raw line count next to it, like `src/main.py (387)`. This gives the chatbot a much better sense of file size before it decides whether to `cat` the whole thing or just `read-lines` a chunk of it. You can turn this off with the new `reptclip.showLineCounts` setting if you'd rather keep the structure listing minimal.

### Move, rename, and explicit delete in diffs

The diff format your chatbot generates picked up two new one-line operations:

- `old/path.txt -> new/path.txt` moves or renames a file without touching its contents.
- `old/path.txt delete` removes a file outright.

That last one matters because the old behavior changed slightly: an empty `REPLACE` block used to mean "delete this file," but only if the `SEARCH` block matched the file's *entire* current contents. That meant deleting a file required the chatbot to regenerate the whole thing, verbatim, inside the SEARCH block, just to throw it away.

![Image description](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/rl633kz9tkwvt00ge7ih.gif)

That's wasted tokens at best, and at worst a single mismatched character in a large file would make the whole delete fail to apply. Now the chatbot just writes `old/path.txt delete` and moves on, no regeneration needed! An empty `REPLACE` block on its own now just clears the matched text and keeps the file (even if that leaves it empty).

### Undo now warns you before it steps on changes

If you hit Undo on an applied diff and the file in question has since been modified, either on disk or with unsaved changes in the editor, ReptClip now shows a warning first instead of silently reverting over your work.

## And... I received my first external PR! 🥳

A huge part of making v2.0 safe to ship came from @mansio, who contributed two PRs to [effessdev/reptclip](https://github.com/effessdev/reptclip), totalling roughly 1,500 lines of code!!! 🤯

The [first PR](https://github.com/effessdev/reptclip/pull/4) focused on security in the diff-applying process. It uncovered several issues, including symlinks allowing writes outside the workspace, the ability to overwrite `.git` files, and Undo/Redo overwriting unsaved editor changes. It also fixed a `.gitignore` parsing bug.

The [second PR](https://github.com/effessdev/reptclip/pull/5) caught even more edge cases, like missed editor changes on case-insensitive filesystems, race conditions during file updates, and incomplete symlink protection that could expose `.git` or `.env` contents to the chatbot. These are now fixed, **huge thanks to @mansio! 🎉**

## A little help goes a long way 🥲

ReptClip wouldn't be quite what it is today without a few people who took the time to share their thoughts and suggestions.

A big shout-out to @unitbuilds for letting me know about the limited-time Qoder promotion. That tip made a huge difference and helped make ReptClip possible! The promotion may be over, but I now have something even better: ReptClip! 😁 In fact, I used ReptClip itself to build ReptClip v2. And I mean **heavily**! 🤯

Thanks to @piekwerk for actually giving ReptClip a try and suggesting that reverting changes should check for dirty editor tabs. I initially overlooked this, but now I get how important that was. In v2.0, both Undo and Redo now check for changes on disk and unsaved editor changes, warning you before proceeding.

And thanks to both @piekwerk and @mansio for pointing out something I hadn't considered: the order in which files are included in a prompt matters! Long prompts can lose effectiveness when important context gets buried in the middle. That feedback led me to make file patterns respect their written order, so you can push the most important files closer to the end of the context (right before your prompt).

For example:

- `**/*.py main.py`: Includes all Python files, but puts `main.py` last.
- `**/*.py src/**/*.py main.py`: Includes all Python files, puts files under `src/` after the other Python files, and puts `main.py` last.

These might seem like small details, but they're exactly the kind of feedback that makes a project better. Thank you all for taking the time to help!
