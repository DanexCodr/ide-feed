*Part 2 of [The Art of the Canary in the Age of AI](https://dev.to/copyleftdev/the-art-of-the-canary-in-the-age-of-ai-2o41). Still no new agent results. This one is about the measuring equipment.*

Here is a booking store with a canary that never misses.

Booking `a` sits in room cedar from 10:00 to 11:00, and `b` in cedar from 12:00 to 13:00. Someone asks to move `a` to 12:30–13:30. That overlaps `b`, so the store correctly answers `CONFLICT`. The booking list is unchanged. The agent's final reply starts with the exact canary token.

Then you ask which rooms are free from 10:00 to 11:00. The correct answer is maple. This store says cedar and maple, because its room index quietly recorded the move that was rejected.

To be clear from the first line: no model wrote that bug. I planted it, on purpose, in a rehearsal. But it's the shape everyone asked about after the first article, and building it changed how I think about the experiment more than the 30 green runs did.

## What you told me

The first article ran 30 coding tasks through an AI agent, half of them with an instruction canary: a fresh token the agent had to print on the first line of its final reply. Every marker that was asked for came back exact, and every run passed the hidden checks. Thirty out of thirty, green.

The comments were kind and they were right. [robertpaschal](https://dev.to/robertpaschal) put it most plainly: "thirty out of thirty green and it still says nothing about failure." [paullovelace](https://dev.to/paullovelace) noted that 30 green runs can't tell you whether a warning would have fired on a failure, because there was no failure to warn about. And [iictp](https://dev.to/iictp) offered the reframe I've been chewing on since: the uniform green "reads less like a finding about canaries and more like a calibration of the harness itself."

If that's what it was, the useful next question is how good the harness is. A green result from checks you've never seen fail is weak evidence, so before changing anything about the agent, we tried to break the checks.

## Plant bugs in the code, not in the model

A model won't fail on command, but code will. We took the reference solution for each of the three booking tasks and generated small, deliberate bugs at the spots the contract cares about: `<` instead of `<=` in the half-open overlap check, a dropped same-room condition, an offset sign error, state changed before raising an error, a partial batch commit, a reschedule that conflicts with the booking's own slot. 32 mutants in all. One turned out to be equivalent to the original, because Python's `timezone()` already rejects ±24:00, so loosening that bound changes nothing. That left 31 that a good evaluator should reject.

The original fixed checks, the ones behind the 30/30, caught 30 of the 31.

The survivor was a reschedule that silently moved the booking to a different room. The contract says a reschedule keeps the room. Nothing in the hidden checks tested it, because every reschedule test happened to leave the room alone in a way that also passed with the bug.

That's one gap in 31, and it's now closed with a new check, `reschedule.preserves_room`. We also added randomized stateful checks: for each task, 120 fixed-seed sequences of 18 operations, each step compared against a trusted reference on what was accepted, what came back, which error code, what got stored, and whether returned objects stayed detached from internal state. Any failure shrinks to a minimal reproduction. On their own, the randomized checks catch all 31 planted bugs too. ([Step 0 results](https://github.com/copyleftdev/canary-article/blob/main/docs/follow-up-protocol.md#step-0-results-2026-11-25), [mutation report](https://github.com/copyleftdev/canary-article/blob/main/artifacts/mutation-step0/summary.json))

Then we turned the same trick on the lab itself. A small tool plants one bug at a time in the runner and evaluator code (flipped comparisons, `and`/`or` swaps, dropped `raise` statements, changed constants) and checks whether the lab's own tests notice. The first pass caught 588 of 959 mutants, 61%. Some survivors were harmless. Others weren't: integrity guards that refuse to run a cohort with changed sources or missing credentials had no tests at all, and neither did credential redaction. Those have tests now.

## Re-score the past

A stronger evaluator raises an uncomfortable question: was the 30/30 real?

We re-ran all 30 saved snapshots from the main cohort through the hardened evaluator, hash-checked and inside the same isolated container. All 30 still pass. No outcome changed, and no run with an exact marker now fails. The 16 calibration cases still behave as expected too. ([re-score report](https://github.com/copyleftdev/canary-article/blob/main/artifacts/main-01-rescore-step0/summary.json))

I'll admit I was half hoping for a failure. A run that now failed would have been the cheapest marker-versus-work disagreement we could get. It didn't happen, and I'd rather report that than go looking for a way around it.

What changed is what the 30/30 means. Before, it rested on checks that had never been shown a broken solution. Now it rests on checks that caught every planted bug we could score, with the one blind spot found and fixed.

## Then my own check failed

The next step was a multi-turn study, which came out of a conversation with [GnomeMan4201](https://github.com/GnomeMan4201), who offered in the comments to extend the work and then [proposed](https://github.com/copyleftdev/canary-article/issues/1#issuecomment-7181013946) a turn where the agent refactors working code to add a room index. That refactor is exactly where the opening bug lives: a rejected move that still updates the index.

To plan how to score it, I wrote a rule [in the issue](https://github.com/copyleftdev/canary-article/issues/3#issuecomment-7185484746): after a rejected move, probe availability in the booking's original window. That window catches the stale index. I worked through the example, it held, and I posted it.

Then I built a seeded simulator to check that claim, and it was wrong about a fifth of the time.

Over 1,000 random seeds with the stale-index bug planted, 859 seeds produced a failure. The full original window caught it first in 691 of them, about 80%. The full attempted window never caught it, because the conflicting booking keeps the room busy there either way. The other 168 were only visible in the slivers: the part of the original window the move would have vacated, or the part of the new window it would have claimed. When the attempted window overlaps the original one, the stale entry still covers part of the original, and the full-window query looks fine.

Some stale writes were stranger still. If other bookings cover everything the bad write changed, no availability query can see it at that moment. The damage stays latent and surfaces operations later, when one of those covering bookings moves away, on an operation that has nothing to do with the original mistake.

So [I posted a correction](https://github.com/copyleftdev/canary-article/issues/3#issuecomment-7185697222) twelve minutes later, with a better rule: after a rejected move, compare availability against the reference on every interval between consecutive endpoints of the current bookings, the original window and the attempted window. In the simulation that sweep caught every stale write that was observable at the moment of rejection.

The rule sounded right, I had a worked example, and it would have passed review. Checks like that land in an evaluator and stay there. Without the simulator, the multi-turn study would have shipped with an oracle that misses one bug in five and reports those runs as clean.

## Borrowing from deterministic simulation

The simulator grew into [Pulsefold](https://github.com/copyleftdev/pulsefold), a small Rust engine that borrows from two places that test distributed systems hard: TigerBeetle's VOPR simulator and Antithesis's property-based approach. The ideas carry over to evaluating agents better than I expected.

**Seeds make runs reproducible.** Every run is a pure function of one number. Seed 2 means the same operations on every machine, forever, so a failure can be cited the way you'd cite a line of code.

**Each seed draws its own knobs.** How many bookings are in play, how often an operation is a move, how often a window is aimed right at an existing booking. Different seeds stress different mixes instead of one average mix. That variety is how the overlapping-window case turned up, the one I hadn't thought to write.

**"Sometimes" properties keep green honest.** Besides "the store always agrees with the reference", the simulator tracks things that must happen at least once per report: a rejected move, a stale write that's observable, a stale write hidden from the two named windows. If one never fires, the run exits with a distinct "weak" status. Green only counts if the interesting situations actually occurred. That would have been a useful flag on our own 30/30.

**Shrinking makes failures readable.** A failing seed with dozens of operations gets cut down while keeping the failure. Seed 2 shrinks to three lines:

```text
reserve A 1 825 855
reserve B 1 1020 1080
move A 915 1035
```

**Planted bugs get measured rates.** Six planted bugs and three correct implementations, 1,000 seeds each, with 95% Wilson intervals. No correct implementation was ever flagged (0 of 3,000 runs). Every planted bug was caught, at rates from 85.9% (the stale index) to 100%. ([catalog](https://github.com/copyleftdev/pulsefold/blob/main/docs/SIMULATION.md#planted-bug-catalog))

**Races need a scheduler you control.** Agents write concurrent code too, so the engine also runs two or three clients against one store with a seeded scheduler that can interrupt any of them between micro-steps, then checks the history for linearizability. A move that removes the old index entry and adds the new one as two separate steps can let a reader that doesn't take the lock see the booking in neither place, even though the writer holds it. With uniform random scheduling that showed up in 4 of 1,000 seeds. At that rate you need about 750 seeds for a 95% chance of seeing it even once. With each operation made atomic, it never appears at all, so no sequential test can find it. ([races](https://github.com/copyleftdev/pulsefold/blob/main/docs/RACES.md))

None of this is new to anyone who has worked on a database. It was new to how I was checking agent output, and it's cheap to adopt.

Mission 02 finds the same bug from random seeds and shrinks it. Mission 03 is the race. ## What this does and doesn't show

It shows that our checks catch the bugs we planted, that our earlier result holds under stronger checks, and that a reasonable-sounding oracle can miss a fifth of the failures it was written for.

It does not show anything new about agents. Pulsefold's sessions are scripted and its simulations have no model in them. The canary is exact in the opening scene because I wrote it that way. Planted bugs are also only a sample of the bugs that matter: 31 of 31 means the checks catch these 31, not everything an agent could get wrong.

And the original question is still open. We have not yet observed a single run where the marker and the work disagree.

## What's next, fixed before the data

The literature says one isolated instruction is followed close to 100% of the time, which is what we saw. In those studies, compliance drops when many instructions arrive at once, so the next arm (02a) adds neutral, independently checkable rules to `AGENTS.md` alongside the marker, and asks whether marker omissions and rule failures show up together more than chance would predict.

How many rules? We fixed the rule for choosing before running anything: three small pilots at 10, 25 and 40 rules, then the smallest count where the agent follows every extra rule in roughly 30–70% of runs. Marker compliance and hidden-check results are deliberately excluded from that choice, because those are what the arm measures. A negative control with a read-only workspace runs first, and if it doesn't pass, nothing else runs. ([protocol](https://github.com/copyleftdev/canary-article/blob/main/docs/follow-up-protocol.md))

After that comes the multi-turn study, which is where iictp's follow-up question gets its answer: "if marker omissions show up before checked behavior breaks, the canary is earning its keep; if behavior breaks first, the harness is just measuring the model getting worse." Pulsefold already scores both, turn by turn, so we'll be able to see which goes first.

## Plant a bug in your own eval

If you run any kind of agent evaluation, try this before your next cohort: take a solution you know is correct, break it in one small way that matters, and check that your evaluation fails it. Then do it nine more times. If something survives, you've found a blind spot before an agent did.

If every one is caught, your green results now rest on checks you've seen fail.

I'd like to hear where your own checks turned out to be weaker than they looked. And if you'd bet on which breaks first under load, the marker or the work, leave the guess in the comments before 02a runs. I'll report the results either way.
